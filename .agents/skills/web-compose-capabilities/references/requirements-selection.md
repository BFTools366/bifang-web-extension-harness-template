# 从需求流程选择独立能力

完整账号保留账号、自有组织、有效成员与个人设置；协作范围明确取消时，选择 session/profile/password.change/organization.switch/permissions.enforce，加按需 register/verification，而非 identity.workspace。自建 Go 账号装配器保留这些核心依赖，只有显式 workspace 才展开邀请/成员/角色 UI。接受邀请不自动获得业务权限，共享业务还须接线负责人授予业务角色的流程。公开浏览不增加注册、订单或钱包；本地工具不增加远端服务；浏览器扩展只按明确动作申请最小权限。

本合同归 `$web-compose-capabilities`；调用方传入已分析的流程、原文依据、已知宿主或宿主未定状态、阶段、角色与数据范围。本 Skill 选择领域能力及适用资源，不负责完整文档语义分析、PRD 确认、实际 UI 设计或代码装配。

## 按操作判断

| 能力                | 采用依据与边界                                                                                                                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 身份认证 `identity` | 明确需要登录、登出、会话恢复或受保护用户数据时选择所需操作；完整用户方案同时满足账号、组织与成员基线，注册成功必建自有组织。找回与第三方登录分别判定；已有可信认证实现复用等效 owner，不另建会话。 |
| 权限 `permissions`  | 明确存在不同角色、动作限制、资源作用域或撤权时选择；管理员名称不能推导权限码、角色写入或服务端授权方案。身份来源和权限获取按真实契约明确归属，访问控制叶子只消费既有上下文。                       |
| 组织 `organization` | 完整用户方案必须包含自有组织、当前组织及成员上下文；多组织切换、邀请/接受与拥有者管理按已确认范围接线。只复用低层会话资源不能证明完整用户已交付，缺少服务或模板时返回缺口，不在客户端补造组织。    |
| 其他能力            | 商品 `catalog`、订单 `orders`、钱包支付 `wallet-payments`、审计 `audit` 按具体读取、写入或恢复操作独立选择；未被模板覆盖的需求返回调用方，不为匹配模板新增模块。                                   |

不按“账户”“团队”“后台”或“SaaS”等关键词打包选取功能。组织与权限可复用已有身份，查看订单不默认带商品、钱包或支付。依赖由具体操作的 catalog 图确定，必要依赖自动补齐并展示原因；不能用独立模块表述绕过购买对基础身份的要求。

完整用户方案的判定来自已分析的用户信息、注册与组织数据范围，遵循[身份基线](../knowledge/identity.md#完整用户信息)，不由应用类别推断。已确认需求包括加入其他组织时，邀请接受和成员关系必须交接，不能只选择 switch 就宣称加入已完成；组织 ID 与成员 ID 的归属分工以组织知识为准。

## 阶段与输出

- 创建前 `creation-analysis`：只读返回模块、操作、原文依据、状态、角色/数据范围、宿主、可用资源与契约缺口；不取代码模板、不调用组装器、不写入工程、不授予权限，完成后返回需求分析调用方。阶段是调用上下文，不是新增配置。
- 下游需求/设计：复用唯一 PRD 和已确认范围，只读所选知识；设计确需参考时读取相应设计资源。不重新收齐文档或改变已选范围。
- 下游实施：返回当前操作适用的 code/design/demo 模板与适配约束，由 `$web-implement-change` 负责装配、真实代码和验证；本 Skill 不独立启动开发、HTTP 接入或发布。

有充分需求依据的能力和最小依赖优先自动选择并说明原因，等价方案或真实争议才推荐并澄清；宿主未定时只分析操作，不调用要求 host 的选择器或读取宿主模板。每项结果给出明确要求 / 自动选择 / 推荐 / 待确认 / 不需要状态。这些是 Agent 内部分析输出，不是用户逐项选择的功能问卷。已确认操作的必需依赖及固定默认行为直接纳入唯一汇总，不再次询问是否启用；仅新增范围或真实业务分歧返回调用方澄清。没有需求依据的能力保持未选；原文没有说明但会扩大范围的选项标待确认，不静默启用。可信身份、权限获取、管理目标、组织作用域与缓存所有者分别记录，不能相互代替。

真实 API、GraphQL 列表 Schema、凭据保存、并发和写入恢复缺口照实保留。浏览器权限与业务权限分开，未知结果先查询而不重放订单/支付；能力建议和模板不授权真实资金、生产访问或权限扩张。详细不变量读取所选模块知识，不在本表重新定义。

## 固定设计与操作依赖

当前可执行资源以 catalog schemaVersion 2 为准。使用选择器计算 requested/resolved/requiredBy，依赖先于使用者；购买 orders.purchase 自动补入基础身份、目录、订单创建与钱包支付，内部写节点不单独暴露选择。权限与组织仍按现有操作加入、依赖基础身份，选择器尚不自动生成完整账号生命周期。完整用户方案需要的组织上下文、账号资料、注册或邀请若不在当前图内，单列为待补齐接线并交还调用方，不能编造 catalog 操作或以最小闭包代替完整需求。完整闭包及补齐范围一次确认，已有批准直接沿用；下游按各能力 design.md 与 application/wiring.md 实施，不能用旧离线 demo 或操作表单宣告接线完成。

## Workspace 服务归属与领域交接

从根 .harness/workspace.json 读取已有服务或自建 Go；已有服务必需 BaseURL，选中操作还要可信 endpoint/Schema；选择 create 则委托对应 implementationSkill 同时完成 Go、前端 typed adapter 和真实联调。交接操作、成员、服务归属、契约、写入范围、最小依赖与验收；叶子返回当前调用方，不要求 Go 初始化问卷，不生成产品 Mock 或演示账号。

## 邮箱注册及组织内页面

明确选择注册时采用邮箱与密码，无需收集用户名或组织名，旧用户名登录保持兼容；已有服务的差异按可信合同处理。自建服务的邮箱注册默认补齐 identity.verification 和后端 verification；无真实邮件服务时默认 dev 模拟投递，发送成功在表单显示验证码，接通 SMTP 并关闭 mock 后移除回显，不另行询问。基础登录不自动增加注册，找回仍使用独立真实通道。

同一组织内业务使用一个导航入口，用户菜单切换组织以读取各自作用域的数据；自有/加入关系不生成两套业务导航。公开登录、注册共用认证布局，设置采用底部低强调文字链接；这些结构交给固定模板消费，产品标题和内容继续来自下游 PRD。
