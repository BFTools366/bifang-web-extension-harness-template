## 正常流程与设计理由

建议核对的操作序列：原单权威状态 → 服务可用钱包 → 用户确认 → 原意图付款 → 未知查询原尝试 → 确认成功后精确读取；只读范围独立成立。

填写本次实际流程、每步输入/输出、何时可执行以及用户可见反馈；解释为何需要此操作及哪些事实支持设计。没有实际合同的部分标为建议或待定，不写成已实现。

## 按需组合与宿主

钱包只读不依赖订单UI；付款需可恢复原单，不要求使用本Harness建单模板；权益/权限刷新只按实际服务关联。

列出本次实际消费的公共对象/操作和被调用方，未采用能力注明不适用；不要把产品名称或“后台”标签当依赖。Web 使用当前 Router/Query/UI；Extension 使用真实 surface、消息/存储 owner 和 Chrome MV3/Firefox MV2 边界，不照搬 Web 文件路由、专属列表 Skill或凭据 LocalStorage例外。能力选择不自动增加浏览器入口、权限或持久化。
