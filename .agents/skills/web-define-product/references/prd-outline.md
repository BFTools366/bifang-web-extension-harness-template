# 下游 PRD 记录约定

此约定只在下游实际需求工作中使用；初始化不实例化此模板，也不创建业务 PRD。沿用 `docs/product_spec/README.md` 的日期、完整快照和唯一当前正文规则。首次需求工作若目录不存在，由 `$web-define-product` 创建索引和当天正文，不能假定初始化已有业务记忆。

PRD 保持与需求规模相称。推荐结构如下，已有项目结构可保留，只补缺少的实质信息：

```markdown
# YYYY-MM-DD 产品规格（PRD）

状态：Draft

## 用户、问题与目标

目标用户、场景、痛点、预期结果与可衡量成功标准。

## 本轮范围

稳定 scope ID、包含/不包含、页面或 Extension surface、优先级。

## 需求与验收

稳定需求 ID；每项写触发、输入、行为、输出及可观察的成功/失败标准。

## 数据与交互

实体/字段、来源与存储、主要状态/转换、异常与恢复；简单需求不强制画图。

## 约束与未决项

宿主、权限、隐私、无障碍、语言、依赖和外部服务边界；待定项的影响与解决条件。

## 确认依据

真实用户确认的日期与原话/会话依据；明确哪些仍是建议或假设。
```

确认只覆盖实际讨论过的范围。没有用户确认时保持 `Draft`；确认需求后改为 `Approved`。单一原型应实现当前已确认需求；业务规则、权限或范围变化必须先回写并确认 PRD。

原型登记是独立事实：每次仅生成一个桌面端可交互 HTML，不做 A/B 比较或 Mobile 设计。`docs/prototypes/<scope>/review.json` 绑定项目实例、设计请求来源、PRD 与唯一原型哈希、登记代次及展示/反馈状态，不做 A/B 选择。需求批准不代替设计反馈；设计变更先展示可打开预览并等待用户反馈，再按当前评审批准开发。完整创建凭据存在时，首版 `initial-create/v1` 的 PRD 保留精确的 `创建确认：<revision>` 和 `创建范围：<七项 scope 的 JSON>` 两行，后者与凭据逐字段一致，并复用已确认七项首版范围；一次性消费规则归设计 Skill，不能用于后续改版。

列表接口设计按 [列表查询协议强约定](../../../../docs/DATA_ACCESS.md#列表查询协议强约定) 记录所需输入与 Schema 依据；无契约时只给待确认设计，不把原型本地数组当作服务事实。

## 能力选择记录

需求分析遵循 [需求分析与界面需求](requirements-analysis.md)，模块及具体操作的判断归 [$web-compose-capabilities](../../web-compose-capabilities/SKILL.md) 及其 [选择合同](../../web-compose-capabilities/references/requirements-selection.md)。本文件只拥有 PRD 的记录结构，不重新定义领域选择规则。

成功下游在唯一 PRD 记录已选模块、具体操作、角色/数据范围、采用依据及日期；建议和未确认项单独保留。已有 PRD 直接复用，局部修复不重启需求确认；创建建议不自动成为 Approved。

| 当前范围               | 具体操作           | 角色与目标/作用域    | 可信契约与缺口       | 所选模板及类型   | 验收             |
| ---------------------- | ------------------ | -------------------- | -------------------- | ---------------- | ---------------- |
| 按当前需求填写所选模块 | 列明读取/写入/恢复 | 区分操作者与管理目标 | 不猜 endpoint/Schema | code/design/demo | 可观察成功与失败 |

模块选择不授予权限或生产/资金操作授权；服务契约缺口保持未确认。

原型的生成、自查和摘要登记由 [$web-design-prototype](../../web-design-prototype/SKILL.md) 拥有；真实功能及相关检查由 [$web-implement-change](../../web-implement-change/SKILL.md) 拥有。它们只消费当前已确认范围，范围变化返回需求定义处理。
