# Web Harness：定义前端产品

把真实问题转化为经确认且可测试的产品范围，不把普通实现细节升级为产品决策。

## Harness 源门禁

先解析当前规范根。若根同时包含 Harness 专用 `Version.md` 和活动 `.agents/skills/web-instantiate-project/SKILL.md`，当前就是模板源，不是终端产品：必须在读取、整理、复述或写入任何下游产品需求前停止产品定义。不得在源根接收、分析、记录或实施产品目的、用户场景、业务规则、成功标准、产品专属 UI/文案/数据、远程凭据、构建或发布需求，也不得生成产品交接摘要。混合请求继续已授权的初始化部分，复用允许字段并转 `$web-instantiate-project`，不吞掉创建动作；只有产品部分要求切换到已存在下游或创建完成后重新提出。Harness 自身规则、Skills、中性模板、验证器和交付工程维护不受此门禁阻止。

## 工作流程

1. 通过 Harness 源门禁后，只在当前已初始化下游工作树由一个 Agent 完成范围设计，不启动写入型并行 Worktree。
2. 要求 `.harness/project.json` 存在且有效，读取其身份与唯一类型；缺失时不得伪造下游身份或继续产品分析。再读取存在时最新 Product Spec，以及与当前问题直接相关的 Status、ADR 和现有 UI；初始化脚手架不是产品意图证据。
3. 确认固定 `projectType`，不得切换或增加第二类型。若需要另一项目，回到源 Harness 只完成固定初始化表单；新下游建立后由用户在该项目根重新提出产品需求，不能把本轮产品内容带回模板源。
4. 先从现有事实提取目标用户、主要场景、输入、输出、痛点、数据边界和成功结果。以下是 Agent 按当前范围检查的维度，不是一次性用户问卷：
   - 按 [功能模块组合](../web-design-prototype/references/prd-outline.md#功能模块组合) 复用唯一 PRD 或本次明确需求的模块、操作与作用域；命中时调用 `$web-compose-capabilities`，只读所选知识，实施需要时再取模板。不按产品分类默认启用功能，不从已安装 Skill 推断授权；范围清楚的日常修复直接返回当前流程。Web 与 Extension 各自遵守宿主边界。
   - Extension 明确 popup/options/content/background 场景、三环境远端服务、站点匹配、Chrome MV3 / Firefox MV2 的权限、API/消息/后台差异、数据存储和宿主限制，既定两目标兼容由执行 Agent 自行保证。
   - 两种类型按真实接入需要确认单一 BaseURL 是否足够或需要多个受控远端基地址；Release 日志细节到接入或发布需要时补齐，不阻断最小 PRD。浏览器公开配置不能被定义为秘密存储。
     按已选认证、组织、权限等操作采用真实页面流程；公开入口、认证页和工作区由需求决定。PRD 记录成功、失败、恢复与设备/键盘流程。
5. 按 [下游 PRD 结构](../web-design-prototype/references/prd-outline.md) 将聚焦结果的目标、`包含`、`不包含`、假设、约束、可靠性/无障碍要求和可观察成功标准记录到唯一 Product Spec（PRD）。给本轮范围和需求稳定 ID；按真实复杂度补数据模型、主线、状态及异常恢复，不为简单需求强制套全部框架。只有缺失会破坏最小完整闭环或安全性时才扩大当前范围。
6. 遵循工程规则“渐进式交互引导”：每轮优先问一个会改变下一步或产品边界的关键问题，用“是否先采用……？建议/默认……，因为……”及简短选项引导。已知答案不重问；可逆低影响项给建议，非阻断未知项标待定并继续。必需的功能启用与范围确认等待明确答案，不虚构权限、数据来源、后端、账号或发布渠道。完整清单由 Agent 逐步补齐，不要求用户一次交齐。
7. 澄清过程中将真实需求记录为当天 Draft；首次需求工作若索引不存在则创建，并遵循完整快照、一天一份及只保留最新正文的规则，不继承上游批准事实。阻断问题逐项处理，给用户可审阅 PRD 后一次确认范围；已有真实确认直接复用。未经用户确认不得标记为 Approved。长期决定单独触发 ADR；PRD 的 Approved 不代替原型生成、自查和摘要登记。
8. 只有在真实发布完成、重要阻断、跨会话交接或用户要求时更新 Status；不要因产品定义自动创建 Work Plan、Verification 或 Changelog。
9. 选择下一行动：
   - 当前没有已初始化下游时停止产品定义；源 Harness 只运行 `$web-instantiate-project` 的固定创建门禁，终端下游不得恢复创建 Skill。
   - 新产品、新页面、显著交互改版或用户要求原型时，已确认 PRD 交给 `$web-design-prototype` 产出一个桌面端可交互 HTML 原型，自查、展示并登记后按已有授权进入开发；不生成 A/B 备选或 Mobile 布局，也不要求用户选择方案。初始化只安装所需项目级 Skills，不运行本流程。
   - 已有有效原型登记且范围未变，或范围清楚的日常小修复、无界面变更，交给 `$web-implement-change`；不得为绕过尚未完成的原型自查登记把新 UI 伪装成小修复。不因多步骤、多文件或用户可见自动创建计划。
   - 只有用户明确要求持久计划、跨会话交接，或发布/高风险工作确需协调时才交给 `$web-plan-change`。
   - 构建、完整验收、E2E、安全、权限、不可逆副作用和发布由明确请求或各自硬要求单独触发，不由产品定义或计划存在自动触发。

## 完成输出

报告目标、范围内/外、成功标准、下游固定的唯一项目类型、权限/隐私边界、未决项、下一项具体行动及适用专用门禁。不选择额外项目类型，不实现业务代码，不预建未触发的项目记忆；命中 Harness 源门禁时不复述或保存被拒绝的产品内容。
