# Web Harness：审查模块边界

为指定范围建立职责与依赖地图，识别真实耦合和重复拥有者；不以文件数量或行数单独决定拆分。

## 触发与边界

- 用户要求结构/职责审查，或实现、重构需要定位实际边界问题时调用。已有地图仍适用于同一源码状态时直接复用。
- 源 Harness 只审查工具、模板、规则或 Skill 结构；已初始化下游按唯一 `projectType` 审查产品代码，不跨宿主预建共享 core。
- 只读，不移动文件、不修改代码或权威记录，不自动运行测试、构建或创建持久计划。实现与行为保持证明由调用方负责；返回后不反向启动调用方。

## 读取与分析

1. 读取工程规则的“文件结构与模块依赖”，以及承载文件规模规则的实际章节（源为“文件规模”，下游为“TypeScript 与职责”），以及当前 Git diff、目标文件和直接消费者。先用 `rg --files` 定位，只有证据跨出范围时扩大读取，不扫描全部历史与专题。
2. 列出每个模块的实际职责、入口/公共符号、输入输出、状态和副作用拥有者。组件、hooks、样式、局部状态与测试按真实功能聚合；API/存储保持数据层归属。
3. 追踪实际 import、重导出和调用方向；报告循环时给出完整路径与相关符号。类型依赖、运行时依赖和动态调用分开，不能把目录命名当执行证据。
4. 检查跨功能私有导入、无稳定消费者的公共层、兜底目录、通用 manager 和转发壳；只对真实重复职责建议提取。业务边界内的小文件可以保留内聚，不为未来复用建立抽象。
5. 核对 Router、Query、Jotai、存储、请求/订阅生命周期及错误反馈的唯一拥有者；对共享 Git/工具元数据同样定位唯一写入者。没有证据的性能问题不下结论。
6. 对拟拆分项给出目标职责、文件位置、单向调用关系、保持不变的公共契约、受影响消费者和相称验证。源门禁与运行时门禁为防共同弱化而独立锁定的规则不合并。

## 返回结果

返回有文件/符号依据的职责地图、依赖与拥有者问题、按风险排序的建议及不宜拆分的部分；未知项明确标注。调用方选择范围后实施，不能把审查建议当作修改授权、行为保持或正式验收结论。
