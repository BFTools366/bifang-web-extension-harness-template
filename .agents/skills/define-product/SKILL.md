# 定义产品

把真实问题转化为经确认且可测试的产品范围，不把普通实现细节升级为产品决策。

## 工作流程

1. 在当前工作树由一个 Agent 完成范围设计，不启动写入型并行 Worktree。
2. 读取 `.harness/project.json`、存在时最新 Product Spec，以及与当前问题直接相关的 Status、ADR 和现有 UI。初始化脚手架不是产品意图证据。
3. 确认固定 `projectType`。产品定义不得把 `web` 改为 `extension`、把 `extension` 改为 `web`，也不得增加第二类型；这种需求应建立新的独立项目。
4. 提取目标用户、主要场景、输入、输出、痛点、数据边界和成功结果：
   - Web 明确路由/页面范围、访问方式、浏览器支持、development/test/release 远端服务与隐私边界。
   - Extension 明确 popup/options/content/background 场景、三环境远端服务、站点匹配、Chrome MV3 权限、数据存储和宿主限制。
   - 两种类型都确认 BaseURL 是否足够或需要受控多 target，并明确哪些日志元数据可在 Release 保留；浏览器公开配置不能被定义为秘密存储。
5. 写出聚焦结果的目标，并列出 `包含`、`不包含`、假设、约束、可靠性/无障碍要求和可观察成功标准。只有缺失会破坏最小完整闭环或安全性时才扩大当前范围。
6. 只询问答案会实质改变产品边界的缺失信息；非阻断未知项标为待确定，不虚构权限、数据来源、后端、账号或发布渠道。
7. 首次确认或产品目标、边界、约束、权限/隐私模型、成功标准变化时，按仓库规则创建或更新当天 Product Spec；长期决定写当天 ADR。未经用户确认不得标记为 Approved。
8. 只有里程碑、重要阻断、跨会话交接或用户要求时更新 Status。不要因产品定义自动创建 Work Plan、Verification 或 Changelog。
9. 选择后续路径：
   - `快速`：范围清楚、局部、可逆、不改变公开行为或权限；直接交给 `$implement-change`。
   - `标准`：多步骤、多文件、中等风险或需交接；交给 `$plan-change`。
   - `里程碑`：首次/变更公开页面或扩展能力、权限与隐私边界、安全高风险或发布候选；交给 `$plan-change` 并要求最终真实产物验收。

## 完成输出

报告目标、范围内/外、成功标准、固定项目类型、权限/隐私边界、未决项、所选任务路径和下一项具体行动。不选择额外项目类型，不实现业务代码，不预建未触发的项目记忆。
