# 下游 PRD 记录约定

此约定只在下游实际需求工作中使用；初始化不实例化此模板，也不创建业务 PRD。沿用 `docs/product_spec/README.md` 的日期、完整快照和唯一当前正文规则。首次需求工作若目录不存在，由 `$web-define-product` 创建索引和当天正文，不能假定初始化已有业务记忆。

PRD 保持与需求规模相称。推荐结构如下，已有项目结构可保留，只补缺少的实质信息：

```markdown
# YYYY-MM-DD 产品规格（PRD）

状态：Draft

## 用户、问题与目标

目标用户、场景、痛点、预期结果与可衡量成功标准。

## 本轮范围

稳定 scope ID、包含/不包含、页面或 Extension surface、优先级。

## 需求与验收

稳定需求 ID；每项写触发、输入、行为、输出及可观察的成功/失败标准。

## 数据与交互

实体/字段、来源与存储、主要状态/转换、异常与恢复；简单需求不强制画图。

## 约束与未决项

宿主、权限、隐私、无障碍、语言、依赖和外部服务边界；待定项的影响与解决条件。

## 确认依据

真实用户确认的日期与原话/会话依据；明确哪些仍是建议或假设。
```

确认只覆盖实际讨论过的范围。没有用户确认时保持 `Draft`；确认需求后改为 `Approved`。单一原型应实现当前已确认需求；业务规则、权限或范围变化必须先回写并确认 PRD。

原型登记是独立事实：每次仅生成一个桌面端可交互 HTML，不做 A/B 比较或 Mobile 设计。`docs/prototypes/<scope>/review.json` 绑定项目、PRD 哈希、版本及唯一原型哈希，不记录用户选择。开发时读取 PRD 和该登记记录，按已有实施授权继续；新增需求改变 PRD 后修订、自查、展示并重新登记，不能复用旧摘要。

## Web 类型与可选能力

本节只适用于已初始化的 `projectType=web`；Extension 跳过，不增加初始化问题、身份字段或环境变量。三个概念分别取证：

- `.harness/project.json.projectType` 是固定宿主身份，只能是 `web|extension`。
- 创建期 `webType` 必须明确选择 `tool-site|saas-client|saas-admin`，三种类型均可创建 Web 工程；SaaS 客户端包含既有合同规定的通用认证与工作区基线。明确选择保留在下游 `README.md` 的“创建交接”中，不写入身份 Schema，不生成业务 PRD 或产品专属页面。
- 下游 **Web 业务类型** 是唯一当前 PRD 中经用户确认的 `tool-site`、`saas-client` 或 `saas-admin`，记录采用依据与日期。首次需求直接复用明确的创建选择，不重复询问；已有已确认 PRD 时以其当前模式为准。创建交接仅是输入证据，不从已安装 Skill、页面名称、接口名称或账号权限推断业务类型。

| Web 业务类型              | 适用能力与关联                                                                                                                        | 不自动纳入的能力                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `tool-site` 工具站点      | 沿用通用需求、原型和实现流程；按真实需求接入服务                                                                                      | 不自动启用 SaaS 认证、凭据持久化、注册、组织切换或购买          |
| `saas-client` SaaS 客户端 | `$web-implement-saas-auth` 的客户端登录、注册/找回、当前用户、组织切换与权限 SOP；明确选中购买后再采用 `$web-implement-saas-commerce` | 不包含平台管理；购买默认关闭                                    |
| `saas-admin` SaaS 大后台  | `$web-implement-saas-auth` 的后台认证及 `$web-implement-saas-admin` 的管理 SOP；管理目标组织与操作者会话分开                          | 不含公开注册、客户端组织切换或客户端购买；钱包/支付默认只读查询 |

SaaS 客户端创建时条件询问购买模块（商品选择、订单管理、钱包管理），明确选择保留在 README 创建交接。首次 PRD 直接复用该明确选择、来源与日期，不重复询问；旧项目缺失记录时在首次相关需求补问，不把建议关闭或沉默当成选择。SaaS 客户端的购买选择在同一 PRD 记录 `saas-commerce: enabled|disabled`、真实选择依据与日期。未选择或缺失时不启用，相关需求补齐选择；只有显式选中才纳入商品购买、订单查询、钱包管理及对应菜单/路由/API。开关不授予权限，也不证明服务端能力。大后台按其独立管理范围采用管理能力，不能复用客户端购买开关扩大写操作。

工作开始与恢复时只读取当前变更需要的模式和开关事实；既有明确采用依据直接复用。缺失事实时，只有依赖该类型的业务工作才补问；公共组件、普通小修复不强制启动产品定义。首次采用类型、启用购买或改变产品边界时由 `$web-define-product` 更新唯一 PRD；日常修复复用现有 PRD 与有效原型登记，不循环调用整套定义流程。已确认业务模式改变仍保持原有 Web 宿主，按实际需求/原型变更处理，不能修改宿主或推断旧功能、权限、缓存可沿用。

| 工作环节             | 必须传递的当前事实                                                                                                                                                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 需求 → 原型          | 当前业务类型、可选能力、范围 ID、权限边界与异常恢复；单一桌面原型遵守当前范围，关闭的购买能力不进入原型                                                                                                                                            |
| 原型 → 实现          | PRD、有效原型登记及相关 SaaS SOP；按功能内聚、单向无环依赖实现，不重新创建第二份业务规格                                                                                                                                                           |
| 实现 → 真实 HTTP     | 只接入已采用范围；按 `docs/API.md` 的 SaaS 关联表核对已有操作与契约缺口，再以真实服务契约确认路径、字段、权限及幂等性                                                                                                                              |
| API 变更 → 模块文档  | 由 `$web-document-api` 仅同步受影响模块与独立索引；REST 纯 Markdown 仅含接口名称、接口说明、请求头、请求动作、请求体、响应体，JSON 体均有示例与字段表，不混入文件地址或工程信息；GraphQL 保留名称/说明与有来源的 Schema，Mock 和未确认契约明确标识 |
| 开发检查 → 候选/发布 | 相关非空开发检查不等于完整验收；候选、E2E、真实支付和发布仍由各自独立事件与授权触发                                                                                                                                                                |

读取 SaaS SOP 是复用当前范围的合同，不额外授权功能、真实 endpoint、生产写入或付费操作；服务端仍是组织归属、权限码、价格、支付方式、订单状态和账户数据的事实源。

### 创建与开发 SOP

1. **在源创建工程**：明确宿主与 Web 类型；仅 SaaS 客户端补问商品购买模块是否需要（包含商品选择、订单管理和钱包管理，建议关闭，等待实际回答），其他类型不询问或接受此字段。逐项补齐名称、标识、源外绝对空目标、品牌及策略，完整汇总后一次确认。三种 Web 类型共用安全 staging 事务、依赖安装与独立 Git 基线；SaaS 客户端按已有认证/UI 合同直接生成通用登录、注册、找回与主工作区，未接服务时明确使用 Mock；其他类型保持中性。不在源收集具体产品需求，不生成产品专属业务、PRD、原型或正式候选。
2. **交接到下游**：创建成功后报告目标根、所选类型与 README 创建交接。切换到该项目后读取其 AGENTS、策略及创建交接；首次需求复用明确类型与客户端购买选择、来源和日期，已有 PRD 则复用其当前模式。缺少创建记录且本次工作依赖模式时才补问，不要求重新填写初始化资料。
3. **确认唯一 PRD**：由 `$web-define-product` 逐项澄清当前目标与页面范围，记录类型、选择来源、日期和可观察验收标准。按下面的模式入口读取合同；复用通用 SOP，只追问当前范围真正依赖的差异和缺项。客户端购买沿用明确创建选择，缺失才补问；建议关闭，明确选中后才纳入 PRD；大后台管理模块按用户范围和服务能力裁剪。
   SaaS 共同基线采用 `docs/MANTINE_UI_GUIDELINES.md`：匿名默认登录，语言与外观收在表单内，登录后完整工作区、侧栏底部上下文和账号菜单；公开营销首页另行确认。先列可观察用户流程，再比较布局，不把业务工具卡片当作完整应用。
4. **生成单一桌面原型**：已确认 PRD 交给 `$web-design-prototype` 生成一个可交互 HTML，覆盖当前范围的成功、加载、失败、无权限和恢复状态；自查并给出唯一原型链接和最短试用路径，截图仅辅助。不生成 A/B 备选或 Mobile 布局，不要求用户选择方案。登记后用 `pnpm prototype:check <scope>` 验证 PRD 与原型未漂移，按已有实施授权继续；已有有效登记直接复用。
5. **实施所选范围**：由 `$web-implement-change` 复用相应领域合同，按功能拆分 UI、会话协调、API 与存储。没有服务配置时只 Mock 未接入的远端 API；本地存储、导航、会话协调和 UI 真实实现。需要真实 HTTP 时按当前操作核对 API 关联与真实契约，再调用 `$web-connect-http-service`；不猜 endpoint，不因真实服务失败回落 Mock。
6. **验证与交付**：执行受影响的非空开发回归，按公开 API 变化同步相关模块文档。分别报告工程初始化、功能实现、Mock/真实 HTTP 与未验证项；正式候选、浏览器/E2E、真实支付及发布继续由各自独立请求或硬要求触发。

| 模式        | 下游首先复用的用户操作 SOP                                                                                                                                                                                                                                              | 必须保留的范围边界                                                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| SaaS 客户端 | `$web-implement-saas-auth` 的 `references/requirements-and-sop.md`：登录 → 获取用户/组织/权限 → 主 UI；头像菜单退出及有多个组织时切换，切换后重新获取上下文；邮箱验证码注册和找回成功后返回登录。会话持久化、路由校验和权限按其 `references/session-contract.md` 实施。 | 购买、订单与钱包默认关闭；明确选中后复用 `$web-implement-saas-commerce` 的购买 SOP，未知支付结果先恢复原订单。      |
| SaaS 大后台 | 复用相同认证 SOP 的登录、退出、找回、当前操作员与后台权限；管理范围复用 `$web-implement-saas-admin` 的 `references/pages-and-sop.md`，逐项确认分类商品、组织成员、订单及配套查询。                                                                                      | 无公开注册、无客户端组织切换；管理目标不改变操作者身份。钱包/支付默认只读，资金写操作与生产访问另行明确契约和授权。 |
