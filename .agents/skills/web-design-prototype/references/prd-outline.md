# 下游 PRD 记录约定

此约定只在下游实际需求工作中使用；初始化不实例化此模板，也不创建业务 PRD。沿用 `docs/product_spec/README.md` 的日期、完整快照和唯一当前正文规则。首次需求工作若目录不存在，由 `$web-define-product` 创建索引和当天正文，不能假定初始化已有业务记忆。

PRD 保持与需求规模相称。推荐结构如下，已有项目结构可保留，只补缺少的实质信息：

```markdown
# YYYY-MM-DD 产品规格（PRD）

状态：Draft

## 用户、问题与目标

目标用户、场景、痛点、预期结果与可衡量成功标准。

## 本轮范围

稳定 scope ID、包含/不包含、页面或 Extension surface、优先级。

## 需求与验收

稳定需求 ID；每项写触发、输入、行为、输出及可观察的成功/失败标准。

## 数据与交互

实体/字段、来源与存储、主要状态/转换、异常与恢复；简单需求不强制画图。

## 约束与未决项

宿主、权限、隐私、无障碍、语言、依赖和外部服务边界；待定项的影响与解决条件。

## 确认依据

真实用户确认的日期与原话/会话依据；明确哪些仍是建议或假设。
```

确认只覆盖实际讨论过的范围。没有用户确认时保持 `Draft`；确认需求后改为 `Approved`。原型候选应实现同一份已确认需求；视觉组织可以不同，业务规则、权限或范围变化必须先回写并确认 PRD。

原型选择是独立事实：用 `docs/prototypes/<scope>/review.json` 绑定项目、PRD 哈希、版本、候选哈希与用户选择。PRD 不重复保存“当前选定方案”；开发时读取 PRD 和该选择记录。新增需求改变 PRD 后重新绑定并展示，不能以旧的选择冒充新范围已确认。

## Web 类型与可选能力

本节只适用于已初始化的 `projectType=web`；Extension 跳过，不增加初始化问题、身份字段或环境变量。三个概念分别取证：

- `.harness/project.json.projectType` 是固定宿主身份，只能是 `web|extension`。
- 创建期 `webType` 是一次性选择，不持久化。工具站点可创建，SaaS 客户端和大后台仍是预留流程；分发 SaaS Skills 不表示创建流程已开放。
- 下游 **Web 业务类型** 是唯一当前 PRD 中经用户确认的 `tool-site`、`saas-client` 或 `saas-admin`，记录采用依据与日期。不得从创建历史、已安装 Skill、页面名称、接口名称或账号权限推断业务类型。

| Web 业务类型              | 适用能力与关联                                                                                                                        | 不自动纳入的能力                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `tool-site` 工具站点      | 沿用通用需求、原型和实现流程；按真实需求接入服务                                                                                      | 不自动启用 SaaS 认证、凭据持久化、注册、组织切换或购买          |
| `saas-client` SaaS 客户端 | `$web-implement-saas-auth` 的客户端登录、注册/找回、当前用户、组织切换与权限 SOP；明确选中购买后再采用 `$web-implement-saas-commerce` | 不包含平台管理；购买默认关闭                                    |
| `saas-admin` SaaS 大后台  | `$web-implement-saas-auth` 的后台认证及 `$web-implement-saas-admin` 的管理 SOP；管理目标组织与操作者会话分开                          | 不含公开注册、客户端组织切换或客户端购买；钱包/支付默认只读查询 |

SaaS 客户端的购买选择在同一 PRD 记录 `saas-commerce: enabled|disabled`、真实选择依据与日期。未选择或缺失时按关闭处理；只有显式选中才纳入商品购买、订单查询、钱包管理及对应菜单/路由/API。开关不授予权限，也不证明服务端能力。大后台按其独立管理范围采用管理能力，不能复用客户端购买开关扩大写操作。

工作开始与恢复时只读取当前变更需要的模式和开关事实；既有明确采用依据直接复用。缺失事实时，只有依赖该类型的业务工作才补问；公共组件、普通小修复不强制启动产品定义。首次采用类型、启用购买或改变产品边界时由 `$web-define-product` 更新唯一 PRD；日常修复复用现有 PRD 与有效原型选择，不循环调用整套定义流程。已确认业务模式改变仍保持原有 Web 宿主，按实际需求/原型变更处理，不能修改宿主或推断旧功能、权限、缓存可沿用。

| 工作环节             | 必须传递的当前事实                                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 需求 → 原型          | 当前业务类型、可选能力、范围 ID、权限边界与异常恢复；同一批原型遵守同一范围，关闭的购买能力不进入候选                                             |
| 原型 → 实现          | PRD、有效选择记录及相关 SaaS SOP；按功能内聚、单向无环依赖实现，不重新创建第二份业务规格                                                          |
| 实现 → 真实 HTTP     | 只接入已采用范围；按 `docs/API.md` 的 SaaS 关联表核对已有操作与契约缺口，再以真实服务契约确认路径、字段、权限及幂等性                             |
| API 变更 → 模块文档  | 由 `$web-document-api` 仅同步受影响模块与必要索引；REST 保留六项及 JSON 字段表，GraphQL 保留名称/说明与有来源的 Schema；Mock 和未确认契约明确标识 |
| 开发检查 → 候选/发布 | 相关非空开发检查不等于完整验收；候选、E2E、真实支付和发布仍由各自独立事件与授权触发                                                               |

读取 SaaS SOP 是复用当前范围的合同，不额外授权功能、真实 endpoint、生产写入或付费操作；服务端仍是组织归属、权限码、价格、支付方式、订单状态和账户数据的事实源。
