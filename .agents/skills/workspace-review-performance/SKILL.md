# Web Harness：审查并发与性能

为指定范围定位会卡死、无界增长或在热路径上浪费的代码，返回有证据、按风险排序的建议。没有可观察证据或基准的性能问题只记为待测假设，不下结论。

## 触发与边界

- 用户要求性能、卡顿、死锁、超时或资源泄漏审查，或实现、重构、Go 服务变更需要先定位真实瓶颈时调用。已有结论仍适用于同一源码状态时直接复用。
- 只读，不修改代码、配置、测试或权威记录，不自动运行构建、压测或完整验收；调用方选择范围后按 `$web-implement-change`、`$go-implement-service` 或对应领域 Skill 实施。
- 只审查当前 diff、目标文件及其直接调用方与被调方；证据跨出范围时才扩大读取，不扫描全仓历史。
- 上游锁定的 Go 资产（见 `go-implement-service/assets/UPSTREAM.json`）与生成物只报告风险和建议的上游修复位置，不建议在源模板直接改写。

## 读取与分析

1. 先读取目标代码和直接消费者；Go 范围读取 [Go 服务](../../../docs/GO_SERVICE.md)“上游能力归属与日常开发”的并发与资源约束，前端读取 [数据访问](../../../docs/DATA_ACCESS.md) §2.6–2.7 与 §3.1 的请求、缓存和截止时间所有权。
2. 按 [检查清单](references/checklist.md) 只读命中的宿主章节：Go 服务、TypeScript/React 前端、Node 工具与测试。未命中的章节不读取。
3. 对每个疑似问题追踪锁、事务、goroutine、订阅、计时器、子进程或缓冲区的唯一拥有者与释放路径；死锁需给出等待环（谁持有什么、等待什么），泄漏需给出无界增长的键或引用链。
4. 区分三类结论：已证实缺陷（有代码路径或复现）、高风险模式（违反清单但未复现）、待测假设（需基准或 profile）。后两类不得写成已发生的故障。
5. 建议优先修正根部机制（统一 helper、连接池或拥有者），不在共享基础设施上叠加特例；源门禁与运行时门禁为防共同弱化而独立锁定的规则不合并。

## 返回结果

返回按风险排序的条目：文件与行、问题、等待环或增长路径、影响、建议修复、相称验证（如 `go test -race`、定向 Vitest、基准或 profile）及不宜修改的部分；未知项明确标注。审查结论不是修改授权、性能达标证明或正式验收。完成后返回调用方。
