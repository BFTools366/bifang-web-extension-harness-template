### LIM-012：Windows 全仓 CLI 回归尚未收敛

- 观察：当前 Windows / Node 26 全仓测试的 CLI 子进程出现 ERR_UNSUPPORTED_ESM_URL_SCHEME（c: 绝对路径），并伴随初始化、升级及 Worktree 测试超时；本次定向账号/团队回归不替代这些失败项。
- 影响与状态：待处理，不能声明全仓测试通过；根因及失败项归属仍需逐项复现，不据此修改现有产品或用户未提交代码。
- 复核条件：专项核对 Windows CLI 启动、ESM 文件 URL 和子进程超时，修复后重跑对应 CLI 及全仓测试。

### LIM-013：上游锁定 Go 资产的并发与资源风险

- 观察：原始 `go-implement-service/assets/go-service` 仍由 `UPSTREAM.json` 锁定。当前生成链已通过 adaptGoLogger 保证请求透传、有界捕获、响应脱敏与敏感键合并，不能将原始 logger 字节的旧问题归到当前生成服务。尚未解决的是 ratelimit 的可信代理、无界访客表、持锁 GC 和缺少停止路径，SQLite 连接池及 busy_timeout/WAL、Ping/迁移超时，以及上游 GraphQL 的复杂度与 Body 限制。下游产品已有的 GraphQL 限制尚未成为通用装配能力。
- 影响与状态：上述剩余并发、资源和查询预算限制待处理；不声称已覆盖所有 Go 运行风险。原始快照继续保留，生成 overlay 与原始来源的状态分开说明。
- 复核条件：沿已有 overlay 或经核准更新的 Go 快照修复剩余项，验证实际生成服务的超限拒绝、取消与资源恢复，并以相关 Go 回归及 go test -race 复核；不以更新知识文档代替实现。

### LIM-014：团队基线的查询与锁顺序

- 观察：`team-baseline` 的 `Context`、成员、角色与邀请列表按行查询（N+1）；`SyncOwnerPermissions` 等逐行插入并在单个写事务内完成；`TeamStore.Write` 依赖锁定操作者行串行化，换到 Postgres/MySQL 时不同管理员的写入可交错或死锁。验证码配额与投递现由安装链中的 verification overlay 原子预留，并有乱序投递核对；旧条件资产的先查后发不代表当前接线，已不属于本条待处理项。
- 影响与状态：待处理。SQLite 单写者下暂不触发死锁，但列表与启动同步随团队规模线性放大往返次数。
- 复核条件：按 `$workspace-review-performance` 清单批量加载、批量写入，按聚合固定加锁顺序；以并发与 `-race` 测试证明。
