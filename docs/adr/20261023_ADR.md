## ADR-20261023-001：GraphQL 仅承载列表和条件 GET 类读取

- 状态：Accepted。依据：用户明确要求仅列表查询或其他有查询条件的 GET 类请求强制 GraphQL，其余请求全部 RESTful。
- 决定：按业务操作语义分类，远端列表含无条件首次读取，以及其他带业务查询条件的 GET 类读取使用 GraphQL Query；无条件读取、路径 ID 详情、当前账号/上下文/权限快照及全部写操作使用 RESTful。传输 POST、返回数组、关联复杂度、资源 ID 和作用域不独立决定协议，不新增 Mutation/Subscription；新持续推送采用可信 REST SSE 合同。
- 事实来源与影响：数据访问规范 §1.2 拥有完整分工；工程规则、Skills、领域表单、发现合同和两宿主派生模板消费同一边界。API 元数据区分列表、条件查询、单对象、写和其他请求，检查器执行双向协议约束；语义分类仍须核对实现与消费者。
- 实施边界：本地账号装配将组织上下文和成员权限快照迁到受认证 REST GET，保留成员/邀请/角色等 GraphQL 列表；锁定上游只作引导与来源，最终生成 SDL 不暴露 health/me。旧外部来源和历史账户 Mock 如实标为协议不符合项，不篡改来源或自动迁移存量下游。
- 替代范围：取代按复杂读取启用 GraphQL、按条件承载位置把资源 ID 详情也归 GraphQL、将无条件 health/me 聚合作为合规示例，以及自动允许 Mutation/Subscription 的旧规则。真实契约、授权、会话、缓存及发布门禁继续有效。
- 理由与风险：协议选择明确且可检查；仅检查元数据不能证明操作分类正确，旧外部合同也可能缺少目标 REST/GraphQL 能力。缺可信合同保持阻断，不猜 endpoint 或宣称迁移完成。
- 验证与调整条件：覆盖协议分类成功/失败、两宿主传播、真实 REST 鉴权与主体拒绝、旧 GraphQL 根字段拒绝及保留列表，日常 Harness 硬门禁继续执行；实际结果留当前回复。执行 Agent 维护，用户修订边界时增量调整；回退源差异不删除下游数据。

## ADR-20261022-005：需求先行与有依据的自动选择

- 状态：Accepted。依据：用户要求从需求采集开始梳理 SOP，优先自动选择，存在争议或多个方案同样适用时才推荐。
- 决定：创建先复用或采集需求，宿主未定不阻断只读分析；根据目标、入口、流程与数据归属自动选择唯一适配宿主、必要能力和纯本地方案，等价方案或真实分歧才推荐。品牌方向沿用同一原则；已有显式决定优先。
- 实施与来源：共享表单以 selection 区分 automatic / recommendation，自动结果不写用户原始 values；analysisRevision 绑定需求全文、范围与显式宿主/服务约束，修订使旧推导失效。自动值及理由进入完整确认摘要，CLI 只收集显式事实，不做关键词分类。
- 边界：自动选择只处理逻辑方案，不编造现成服务存在性、地址、权属、保存位置或副作用授权。需要服务时补尚缺事实，明确没有后 create；确定纯本地可自动 none。完整创建确认、下游固定宿主、原型反馈和真实服务合同继续适用。
- 替代范围：修订创建必须先问宿主、纯本地必须逐项选择及品牌无条件三选一的流程；其余工程、数据归属、权限和候选门禁继续有效。
- 风险与验证：语义判断由 Agent 给出并可审阅，机器层验证结构、修订、优先级、来源和写入门禁；覆盖自动/推荐、显式覆盖、需求文件及范围修订、未知服务事实和完整确认失效。实际命令结果留当前回复。
- 调整条件：用户修订需求或显式选择时只重新分析受影响范围，保留其他事实；不更改已初始化下游宿主或迁移业务数据。执行 Agent 维护，后续流程变化按新授权调整。

## ADR-20261022-004：需求场景与执行合同一致

- 状态：Accepted。依据：用户要求用不同需求场景验证诉求理解与后续表单，并直接修正问题。
- 决定：服务来源支持显式 none，用于纯本地且不联网的需求；没有现成服务仍默认创建 Go。none 不生成服务端、健康检查或远端地址，Release 空地址例外仅属于有效登记的本地成员，升级保持模式。
- 范围收敛：账号核心保留自有组织、有效成员、个人设置和按需注册验证；只有显式完整协作才展开 identity.workspace，取消的协作入口不能由装配器恢复。组织共享业务须接负责人授予相应业务角色，成员资格不等于业务授权。
- 表单：修订服务来源使旧地址/契约失效；全部问答阶段接受已知字段修订并保留其他答案，预览与执行均校验同一服务事实。文件后补文字先合并完整正文再交接，原文件保留。
- 替代范围：修订前序“没有服务必建 Go”和“完整用户必展开协作”的限制；组织数据归属、真实服务要求、发布授权与既有项目保护继续有效。既有产品收敛采用增量修改，不重装、不删除业务数据。
- 风险与验证：覆盖两宿主纯本地生成、环境及升级、模式冲突、修订/确认失效、核心账号真实接口与完整协作回归。实际验证结果留当前回复。

## ADR-20261022-003：账号四项菜单与组织导航分层

- 状态：Accepted。依据：用户明确要求账号下拉只保留邮箱/昵称、可点击组织名、个人设置和退出；组织管理与加入放左侧一级分组的两个子菜单。
- 决定：沿用统一“组织”术语，Web 左侧组织管理分组下为组织设置、加入组织；组织名称在账号菜单直接点击切换，不另列角色或重复切换项。管理子项按有效权限 code 显示，加入不要求管理权限。Extension 以紧凑形式保留同一导航层级。
- 个人设置：完整 identity.workspace 默认包含 identity.profile 与 identity.password.change，生成账号级 /account/settings。邮箱只读、昵称可改、密码可改；昵称修改由本地 PATCH /api/v1/auth/profile 实现并权威刷新，改密沿用全账号撤销及回登录。昵称未知写入先重读实际值，改密未知不自动重放；不新建会话或持久化档案。
- 替代范围：取代 ADR-20261020-001 中组织管理/加入位于账号菜单及侧栏仅工作台的布局决定，取代资料只有注入槽的生成限制。ADR-20261022-002 的默认创建、验证、组织隔离和自然语言规则继续有效。
- 理由与影响：区分个人账号动作与组织管理，保持账号摘要清楚、组织入口稳定。低层 identity.session 不扩大能力，已有服务按可信合同适配，不自动改造既有产品。
- 风险与验证：新昵称接口必须只修改认证账号且保留邮箱、组织与凭据；验证菜单内容/顺序、子菜单权限及直达、组织名称切换、昵称刷新与未知恢复、改密退出及旧凭据失效，两宿主生成源码分别执行。
- 负责人及恢复条件：执行 Agent 维护；用户改变信息架构或本人资料范围时按新请求调整。源差异可审查恢复，不回退或删除下游账号数据；实际验证结果留当前回复。

## ADR-20261022-002：默认创建设置、邮箱验证与组织交互

- 状态：Accepted。依据：用户明确要求创建时默认预设、不再询问；无邮件服务仍默认模拟注册验证并在表单显示；文案自然简洁；按组织切换数据并统一称呼。
- 背景：策略模式被强制补问，注册验证依赖额外选择；开发回执已有验证码但页面隐藏。需求分析未前置约束组织归属，界面混用组织与团队并暴露 UTF-8 等实现用语。
- 决定：新创建默认采用既有五项预设，在最终汇总展示；主动自定义时复用并只补缺项。自建邮箱注册自动接通验证码，未配置邮件服务时仅 dev 默认模拟投递，发送后在当前表单显示实际码与简短未接邮件提示；接通 SMTP 同时关闭 mock，真实回执省略 code 并自动隐藏回显。账号、哈希校验、时限、限额及事务单次消费继续真实执行。
- 组织与内容：账号始终拥有自有组织；加入其他账号是加入其组织，保留自身组织。业务保持一个入口，只读取当前组织数据，通过切换查看其他组织；无加入需求仍保留组织边界。用户界面统一称“组织”；标题、标签、占位、反馈和可访问名称使用自然语言，删除重复与实现说明。内部 Team*、team.* 和 wire 标识保持兼容。
- 替代范围：修订原实例化策略必问题、注册验证另选、开发回显禁止及组织选择按来源分组的规则；不改变现有 RBAC、真实业务服务要求或已有服务的可信合同，不迁移存量产品。
- 影响与理由：减少重复问答，使无邮件基础设施时的注册闭环可操作，并让数据归属与用户看到的组织上下文一致。唯一规则仍归 Agent Policy、验证码 Skill、ACCOUNT_OWNERSHIP 和 UI 规范。
- 风险与验证：开发验证码不得进入非开发回执、日志、URL 或持久存储；验证默认物化、自定义冲突、发送及清除回显、真实回执隐藏、验证码消费、组织切换与隔离。实际结果留当前任务回复，不以模板测试代替具体下游验收。
- 负责人及调整条件：执行 Agent 维护；用户后续明确变更默认值或组织交互时按新范围调整。回退源差异不删除下游账号或业务数据，接入真实邮件后关闭开发模拟。

## ADR-20261022-001：可复用的团队数据归属与完整 RBAC

- 状态：Accepted。依据：用户授权将用户、团队、成员、邀请、角色和权限前后端接线固定到 Harness，强调数据归属，并明确前端只按权限 code 授权、后端实现真实 RBAC。
- 背景：此前完整用户基线主要是知识和设计；原始 Go 快照没有邀请或 RBAC，成员 actor 分区也不能代表团队共享归属。按 owner 角色名判断前端入口不符合权限码合同。
- 决定：账号是全局身份，每个账号事务创建唯一自有团队和 owner 成员；加入其他团队只增加成员关系。八表模型通过团队成员、成员角色、团队角色、角色权限和权限目录计算有效 code，所有成员含 owner 都没有授权旁路。共享资源按团队归属，成员私有资源按团队及成员归属，创建者仅用于审计。
- 实施边界：本地用户安装器在固定上游之上装配中性 Go overlay、真实 GraphQL/REST、SQLite 事务与复合外键；完整前端 identity.workspace 和 Go 装配 helper 接通团队恢复、邀请、角色与成员管理。前端只依据有效 code，后端每次校验 RBAC 和真实对象归属；有 team.manage 的非 owner 成员同样可管理，但不能授予自身没有的权限或修改受保护 owner/member 对象。
- 替代范围：取代 ADR-20261020-001 中仅文档批准、运行时尚未装配及按拥有者开放管理入口的限制；其余账号菜单与宿主布局决定继续有效。低层 identity.session 保留，但不代表完整用户系统。
- 理由与影响：ToC 使用自有团队，ToB 以相同租户边界加入协作；角色可配置而动作授权保持稳定。唯一数据归属合同见 [ACCOUNT_OWNERSHIP.md](../ACCOUNT_OWNERSHIP.md)，接口见 [Go 客户端合同](../GO_CLIENT_CONTRACT.md)。
- 风险与验证：需验证开户全事务回滚、邀请状态与并发、跨团队外键与查询、私有资源、角色联合/撤权及无 owner 旁路，并以真实服务核对两宿主接线。源码测试不替代浏览器、最终候选或生产迁移验收；实际结果仅留当次回复。
- 调整与恢复：不自动迁移既有产品、存量账号或商业数据，不把 SQLite 锁语义外推其他数据库。变更自有团队不变量、数据分区或公开权限合同须另行确认迁移；源模板修改可按差异恢复，已有数据不得通过回退代码删除。

## ADR-20261020-002：Workspace 与按领域协作的真实 Go 服务

- 状态：Accepted。依据：用户本次明确要求学习 Go Harness、组合创建 Workspace、按已有服务与自建服务接线、拆分协作 Skills 并取消前端业务 Mock。
- 背景：原入口把独立单包、宿主互斥、空地址 Mock 与前端限定写入生成事务、规则、表单及能力资源，不能只把目录改名或复制后端问卷。
- 决定：新下游根拥有唯一 package.json 包装器、Git、pnpm 锁、策略、PRD 与 API 文档；按实际选择创建 <id>_web、<id>_extension、<id>_server，成员内部保持单宿主和单向模块边界。已有服务必填开发 BaseURL，可信接口按操作核对；没有服务同时创建并连接 Go 成员，不另开 Go 初始化问卷。
- 能力：领域 Skill 协调用户、组织、权限、商品、订单、钱包与审计；Go 叶子拥有服务、持久化、GraphQL、真实验证码、文件、子进程、本地构建与测试。产品只接真实 typed API，测试替身留在隔离测试。未实现操作必须由领域 Skill 增量实现，能力清单不能冒充已完成代码。
- 来源与适配：Go 资产固定提交与逐文件 SHA-256，保留原许可；旧问卷、Mock、发布状态不迁入。账号注册补齐自有组织及 owner 成员的同事务创建，profile 权威验证完整关系。gqlgen 引导输出是精确路径、固定字节的真实生成物，人工文本行数豁免只适用该文件，后续按 SDL 重新生成。
- 替代范围：取代前序决定中的“新下游必须平铺互斥单前端”和“未配置业务 API 运行 Mock”路线；既有独立前端仍原地维护。Workspace 原地工程升级已按专用逐路径合同补齐，见 [升级合同](../../.agents/skills/web-upgrade-harness/references/workspace-upgrade.md)；跨拓扑目录迁移仍须另行明确范围。
- 理由与影响：需求、接口、前后端实现和联调成为同一结果；生成仍只承诺工程事务，完整创建必须继续完成用户选定首版。
- 风险与验证：现有服务不能从 BaseURL 猜接口；发送通道、支付、部署与生产数据副作用仍按真实合同和授权。需验证组合生成、事务回滚、共享锁/策略、原型根归属、HTTP 协议桥、真实注册与持久化、错误及退出失效。具体执行结果留当次回复，不写入本条作为固定事实。
- 调整与恢复：现有下游不自动迁移，源变更可按审查差异回退；产品身份、持久数据与服务归属变化另立迁移合同。详细事实归 [Workspace](../WORKSPACE_TEMPLATE.md) 与 [Go 服务](../GO_SERVICE.md)。

## ADR-20261020-001：完整账号与组织基线及账号菜单归位

- 状态：Accepted，仅表示通用设计与接线规范获准，不表示运行时代码或发布候选已验收。
- 依据：本会话用户审阅账号与组织交互原型后，明确回复“确认，按这版更新知识库与接线规范”。本次授权覆盖知识库、固定设计和接线规范，不覆盖运行时代码改造。
- 背景：知识层把注册自有组织限定为另选生命周期，账号资料只有槽位，旧侧栏展示组织区；相关 Mock 使用成员 actor 分区，不能代表组织共享数据的租户边界。
- 决定：完整用户信息包含 Account、当前 Organization 和有效 OrganizationUser；每个注册账号原子获得一个自有组织及 owner 成员，加入他人组织只新增成员。organizationId 是组织数据的租户边界，OrganizationUser.id 是成员授权主体、成员私有范围及审计操作者。详细不变量归[身份知识](../../.agents/skills/web-compose-capabilities/knowledge/identity.md#完整用户信息)及[组织知识](../../.agents/skills/web-compose-capabilities/knowledge/organization.md)。
- 布局：Web 工作区默认侧栏仅工作台与底部设置；账号信息、当前组织、切换、拥有者组织管理、加入与退出集中在右上账号菜单。单组织仍保留工作区侧栏与加入入口；Extension 按宿主采用紧凑导航。详细结构归[UI 规范](../MANTINE_UI_GUIDELINES.md#81-功能组合的页面与布局)和[固定设计](../../.agents/skills/web-compose-capabilities/templates/application/design.md)。
- 替代范围：修订早期完整用户方案可仅依赖基础身份及按来源布局推导的目标要求，统一按[身份知识](../../.agents/skills/web-compose-capabilities/knowledge/identity.md#完整用户信息)及[应用接线合同](../../.agents/skills/web-compose-capabilities/templates/application/wiring.md)执行。低层认证 helper 和当前 catalog 的独立性继续保留，但不能代替完整用户信息或缩减已确认需求。
- 影响与理由：统一注册、邀请、切换与数据边界，避免账号加入别人组织后丢失自有组织，避免把成员 actor 当全部组织数据键，并使低频账号操作离开默认侧栏。
- 风险与边界：不改当前 catalog、应用装配器、fixture 形状或运行时，也不迁移既有账号与业务数据；不编造邀请 endpoint、权限码、签发、自动登录或凭据持久化授权。原型的注册后直接进入仅为演示，真实服务合同优先。
- 验证要求：知识与布局引用保持一致；后续实现覆盖注册原子性、邀请前后成员资格、自有组织保留、同组织授权共享/跨组织拒绝、owner/member 入口、干净侧栏及切换未知结果恢复。当前实现差异由[接线合同](../../.agents/skills/web-compose-capabilities/templates/application/wiring.md#当前装配器与目标规范的差异)列明，在[技术债](../TECH_DEBT.md)跟踪，不以文档批准冒充已实现。
- 负责人及调整条件：执行 Agent 维护规范，用户决定范围；后续授权实现时按可信服务映射并补行为证据，调整账号/组织不变量或菜单基线须有新的明确决定。

## ADR-20261022-Auth：固化完整 Auth 前后端标准

- 状态：Accepted。依据：用户确认组织管理交互及前后端实现后，明确要求“固化到上游 Harness”“前后端的设计都固化”。
- 决定：采用独立个人设置／改密、账号菜单切换组织弹窗、组织管理三个子页、11 项精确权限及读取依赖；拥有者通过受保护角色取得全权限，成员按角色并集授权。前端模板、Go overlay、接口 adapter、装配器与知识库共同承载，详细合同见 [Auth 标准](../ACCOUNT_OWNERSHIP.md#前后端标准交互与权限表)。
- 边界：不引入个人空间、产品专属权限或业务首页，不改固定 Go 来源快照；核心账号与完整协作仍按明确操作选择。既有产品不自动迁移。
- 替代：取代本文件早期 ADR 中混合个人设置、账号菜单组织管理／加入入口及两子菜单的布局描述；账号／组织／成员不变量保留。旧 team.manage 只用于幂等迁移到原有十项管理权限，新增昵称权限不扩大旧自定义角色。
- 验证：同步验证两宿主生成源码、真实 HTTP 组织与权限流程、版本冲突、未知恢复、服务重启及迁移，执行 Harness 自校验；本决定不代表正式发布或外部服务升级。
