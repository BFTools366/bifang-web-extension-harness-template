# 2026-09-09 架构决定

## ADR-20260909-001：采用事件驱动 Agent 执行与统一进度标题

- 状态：Accepted
- 背景：旧快速/标准/里程碑分级把普通实现、持久计划、并行、构建和完整验收耦合，容易制造无关步骤；不同 Session/Task/Subagent 标题也无法统一表达真实阶段。
- 决定：日常范围清楚工作直接实施；Work Plan、并行、构建、E2E、完整验收和发布分别由独立事件触发。普通 Session、左侧 Task 和内部 Subagent 统一使用 `{序号}|{Task简述}|{当前进度} |{功能摘要}` 四段标题与四态转换。
- 影响：`AGENTS.md`、Agent Policy、Skills、初始化输入、生成下游模板和 validator 使用同一语义；稳定 policy 字段 `milestone_smoke`/`milestone_e2e` 仅保留兼容名称，不再代表任务等级。
- 理由：把执行成本与真实风险或授权事件绑定，同时让跨执行形态状态可观察。
- 风险：宿主标题 API 失败时 UI 可能滞后；失败只报告且不阻断已经完成的工程结果，绝不虚写 `已完成`。
- 验证：schema 正负向测试、生成下游静态断言和任务标题回读。
- 调整条件：只有宿主提供更强的原子标题/状态协议时才替换；字段顺序和阶段集合变化需新 ADR。

## ADR-20260909-002：初始化冻结 source 事实并一次落盘策略

- 状态：Accepted
- 背景：长时间实例化可能在复制过程中读取到不同 source 状态；逐步写入未决 policy 会让失败目标暴露中间决策。
- 决定：在任何 staging 写入前完成项目字段与条件 policy 决议，绑定 source 全部受管文件的路径、字节、普通权限、`Version.md` 和可用 Git 身份；复制冻结字节，并在原子发布前复核 source 未漂移。最终 policy 一次写入且不含 `pending`。目标侧以同名 sibling 租约串行化受支持入口，并冻结父目录、staging、holding 与预存空目标身份；漂移时拒绝发布或清理替代树。
- 影响：交互式初始化首轮批量收集基础字段，再按选择追问；非交互模式显式提供 policy mode 与确认来源。提交点后的 holding 清理异常报告为“已发布但有残留”，普通发布失败保留原空目录 inode。
- 理由：保证发布目标对应单一可复核输入快照，失败只留下可回收 sibling staging。
- 风险：大仓库快照增加少量 I/O；本 Harness 排除依赖和构建产物，成本受控。Node 标准库没有跨平台目录 `rename-if-absent`，因此租约只约束受支持 Harness 入口；故意绕过租约且命中最终复核到 rename 窗口的同机进程不在协议保证内。
- 验证：source 文件/Version/Git 漂移、符号链接根、无效 policy 零写入、合作并发租约、父目录替换、目标出现、原空目录 inode 保留和原子发布回归。
- 调整条件：只有能提供等价内容寻址、模式与 Git 绑定的事务式文件系统接口才可替换。

## ADR-20260909-003：下游升级使用不可弱化所有权与候选/目标双基线

- 状态：Accepted
- 背景：单一摘要无法区分 upstream 更新与下游本地偏离；目录复制会覆盖产品代码、身份、品牌、策略和项目记忆。
- 决定：升级器只接受自身生产 ownership manifest，未知路径默认 `protected`，文档默认 `merge-sections`，并为每个受管/混合路径记录上一轮 candidate 与 target 双快照。每轮先生成外部只读 plan；只对批准的现有 managed `update` 原子应用单路径，每次写入后重规划，混合/新增/删除人工收敛，最后 record。
- 影响：protected/tombstone、unknown、required source 传播、符号链接/特殊文件、Git/计划漂移全部失败关闭；所有权清单与 lock 精确绑定当前目标仓库。计划顶层稳定汇总阻断、人工处理与结构问题，阻断计划和 CLI 错误统一以退出码 2 暴露。读写从稳定根逐级拒绝符号链接并绑定目录身份，复核目标快照后执行临时文件 fsync、原子 rename 与父目录 fsync。record 在锁文件写入前再次完整复核计划；升级器自身的 runner 始终最后更新。
- 理由：三方事实能稳定识别 `update`、`preserve_local`、`conflict` 和 `manual_merge`，同时把授权限制在可审查路径。
- 风险：初次 bootstrap 需要人工收敛重叠 managed 路径；这是缺少可信共同祖先时的必要成本。
- 验证：隔离 Git fixture 覆盖 bootstrap、双基线、managed apply、manual merge、tombstone、required 缺失、计划漂移、跨仓库控制文件、祖先目录符号链接竞态、升级器自更新顺序，以及真实 CLI 的稳定 JSON 与退出码。
- 调整条件：只有新的 schema 保持同等或更强的双向来源证明与本地保护时才可迁移。

## ADR-20260909-004：模板源拒绝下游产品业务

- 状态：Accepted
- 背景：若 Agent 在 Harness 源先分析或整理下游产品需求，即使暂不落盘，也会把模板工程与尚未建立身份、宿主和记忆边界的产品语义混在一起。
- 决定：源根只接收 Harness 自身维护和当前初始化表单固定字段；任何下游产品目的、场景、业务、专属 UI/文案/数据、远程凭据、产品构建或发布需求在读取、分析、复述或记录前拒绝。产品定义只允许在含有效 `.harness/project.json` 的已初始化下游进行。
- 影响：混合请求只能解析允许的初始化字段；实例化成功或切换到既有下游后，用户必须在该唯一项目根重新提出产品内容。源 Product Spec、ADR、Changelog 与计划只记录 Harness 自身事实。
- 理由：确保源模板永远保持产品中立，并让每项产品事实从一开始就归属于唯一终端仓库。
- 风险：用户需要在新项目中再次提出产品需求；这是避免无归属业务语义和跨项目泄漏的必要交接点。
- 验证：源/下游识别、混合请求拒绝以及 `web-define-product` 下游准入由 Harness validator 与生成下游检查覆盖。
- 调整条件：只有未来存在能在写入前证明目标唯一身份与隔离记忆的原子交接协议时才可替换。

## ADR-20260909-005：下游以唯一中性提交建立所有 Task 基线

- 状态：Accepted
- 背景：无 HEAD 的新下游无法满足 Git Task 与内部 Worktree 必须从干净已提交基线创建的门禁；只约束非产品 Task 还会让产品写入 Task 的起点未定义。
- 决定：初始化请求自身授权在 staging 全部脚手架检查和裁剪完成后配置受管 repo-local 身份/模板，并创建恰好一个 `chore: initialize project` root commit；不配置远端。此后所有 Git Task 都从派发前解析并记录的完整已提交 OID 创建，创建后精确复核，不携带未提交状态。
- 影响：新 Web/Extension 下游立即具备可复现 Task/Worktree 基线；只读、Harness 维护和产品写入 Task 使用同一 OID 规则。提交之外的远端、推送、标签和发布仍需独立授权。
- 理由：以一个中性、可审查、无远端的本地提交闭合初始化与并行治理，而不引入桌面分支发布链。
- 风险：身份或模板冲突会在原子发布前阻断初始化；失败 staging 仍按现有安全清理规则处理。
- 验证：实例化需证明单一 root commit、精确主题、clean、无远端；Task/Worktree 门禁需覆盖缺少提交、OID 漂移和未提交状态拒绝。
- 调整条件：只有 Git Task 基础设施支持等价的不可变内容快照身份时才可替换提交 OID。

## ADR-20260909-006：根 Agent 入口预算化并机械拒绝计划状态矛盾

- 状态：Accepted
- 背景：仅按普通文本上限检查根 `AGENTS.md`，无法防止它重新膨胀为初始化、构建、发布和验收规则副本；按日 Work Plan 只校验路径与索引，也无法阻止未完成 Todo 与候选已验收/发布就绪结论并存。
- 决定：根 `AGENTS.md` 固定为合法 UTF-8、最多 20000 bytes 和 120 个物理行的渐进式入口，只保留稳定章节、按需路由、始终生效边界、Skills/约束地图与最小闭环，并机械拒绝代表性的实现级配方回流。活动 Work Plan 必须可解析稳定 Todo ID 与四态；只要存在非 `done` Todo，就拒绝 `accepted`、`ready`、`passed`、已验收、已就绪、可发布或等价候选结论。
- 影响：`pnpm validate:harness` 在普通 Markdown 链接和文件规模检查之外，先验证根入口字节、编码、章节与渐进语义，再验证唯一当前 Work Plan 的状态一致性；计划仍只由原有独立事件触发，不因新增门禁自动创建。
- 理由：把高频入口保持在可控上下文预算内，同时让计划的机械状态不可能领先于真实实施与候选门禁。
- 风险：稳定入口文案或章节改名需要同步 validator；候选结论的自然语言存在表达差异，因此机械规则只锁定明确的状态/结论形态，未来扩展负例时不得误伤未来条件或待办描述。
- 验证：真实入口正例、无效 UTF-8、字节/行数超限、渐进语义缺失、详细配方回流，以及未完成 Todo 搭配英文/中文验收和就绪结论的正负回归。
- 调整条件：只有宿主提供更强的分层指令载入与结构化计划状态协议时才可替换；放宽预算或允许未完成 Todo 获得候选肯定结论需要新的明确决定。
