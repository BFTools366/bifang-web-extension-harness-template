# 2026-10-09 架构决定

## ADR-20261009-001：下游以用户选定原型衔接产品开发

- 状态：Accepted；依据用户本轮明确要求下游需求澄清、PRD 记录、原型选择后开发，并确认默认 2–3 个交互 HTML 方案。
- 背景：现有产品定义可直接交接实施，缺少可比较原型及对具体版本的持久选择；初始化与产品开发需要保持独立。
- 决定：复用 web-define-product 将唯一 Product Spec 作为 PRD，新增原创 web-design-prototype 产出、自查和展示方案，真实用户选定后由 web-implement-change 开发。选择 helper 绑定当前项目、PRD、候选及 SHA-256，漂移后重新展示和选择。
- 影响：两类下游初始化仅分发项目级 Skill、参考、工具与发现元数据，不运行流程、不增加表单、不生成业务记录、不污染全局。源 canonical Skills 为 18，Web 为 16，Extension 为 15，另有独立设计支持 Skill。升级保护产品原型和选择记录。
- 规模复核：`finalize.ts` 为 598 行，本次只增加同一终端化职责中的工作流说明及 Skill 地图，README/Agent 输出仍共同依赖当前宿主配置，保留在现有模块；没有为一行净增加引入额外转发层。
- 理由：复用既有需求事实源，同时让可审阅的设计和用户选择成为新 UI 实施的前提，日常小修复保留直接实施。
- 风险：整份当前 PRD 的字节变化会使选择失效，包括跨范围更新和日期快照变化；需重新展示并确认，不能静默重算。工具不能认证用户原话真实性，调用 Agent 必须对照会话；HTML 不能证明真实接口、权限或最终浏览器兼容。
- 验证合同：两宿主真实初始化 fixture 验证完整分发和业务记录缺席；非空回归覆盖选择、漂移、最新 PRD、输入边界及下游 CLI，独立行为评估覆盖等待选择与小修复分流；源日常门禁验证治理合同。
- 恢复/调整条件：修改选择或 PRD 记录合同须保持真实用户选择和唯一需求来源；不能让推荐、超时或静默摘要刷新代替确认。参考项目仅标注 Internal use only，因此只参考阶段方法，不复制分发其文本和资产。

## 延续的 2026-10-08 决定

## ADR-20261008-001：未配置 BaseURL 时由 API 层 Mock，真实联网按需迁移

- 状态：Accepted；依据用户明确要求无 BaseURL 时全部服务数据在 API 层 Mock，提出真实联网后询问各类 BaseURL 并替换为真实 HTTP 请求。
- 背景：三环境地址已经允许延后配置，但实施 Skill 笼统禁止 Mock，空地址也仅保证静态页面启动，未定义产品数据开发与后续接入的边界。
- 决定：对应环境/服务地址未配置时，由 `src/api/<domain>/` 提供完整类型化异步 Mock API；UI、route、hook 和 Query 只消费同一领域函数。用户要求联网后复用有效配置、收集缺失环境和实际服务地址，确认 endpoint 契约并替换对应实现。真实请求失败不回落 Mock。
- 影响：数据访问规范成为 Mock/真实迁移的唯一详细流程，运行配置负责按需询问与地址校验；工程规则、实施 Skill 和两种下游生成文档同步。中性源不生成业务 Mock，不新增运行时切换框架、依赖或权限；HTTP 空地址拒绝与 Release 非空 HTTPS 门禁继续有效。
- 理由：数据边界集中在 API 层，允许无服务配置时开发完整功能，同时使真实接入可替换、可验证，不让样例数据掩盖真实服务故障。
- 风险：Mock 与真实契约可能漂移，切换后的缓存可能保留样例；迁移需校验外部响应、清理旧缓存，并明确报告未接入/未验证服务。Mock 结果不能作为真实联网证据。
- 验证合同：两宿主空配置初始化回归检查生成规则和 Skill，源日常门禁检查文档/工程完整性。实际业务首次实现须覆盖 Mock 零网络调用、真实成功和最高风险失败不回落；真实服务、权限与浏览器由对应下游事件验证。
- 恢复/调整条件：用户改变默认数据来源或真实服务契约时同步权威规则与对应 API 实现；不得通过错误 fallback 或散落 UI Mock 绕过本决定。

## ADR-20261001-003：HTTP 会话拦截与 Router/UI 采用统一错误语义

- 状态：Accepted；依据当前用户确认统一 401、403、其他错误及自动 Token 读取/写入，并配合路由和 UI。
- 决定：请求层统一标准 header、可信 2xx 提取和显式 Token setter；惰性 applicationHttp 是单个执行上下文的会话 owner。401 single-flight 清当前会话，403 保留会话；handler 每次异步副作用前检查 signal/revision，旧 401 不影响新登录。
- UI：Web 与 Extension 两入口 Router、Query 和直接请求共享固定 i18next 错误分类与 Mantine 反馈。Query 通过 requestHttpQuery 抑制中间尝试提示，仅安全读取有界重试；mutation 不自动重放。局部/路由接管只清同一错误，全局合并同语义播报并以最新失败持有清理权。
- 边界：Token/continuation 只留内存，不新增登录页、refresh、业务 endpoint、跨上下文共享或浏览器权限。真实认证 feature 负责旧私有 cache 清理与受控导航；没有真实登录入口时显示认证状态，不能伪造导航。
- 验证合同：执行生成客户端、Web/Extension 真实 Router/Query/Mantine 组件的非空回归并检查生成 TypeScript；真实网络、CORS、Chrome/Firefox 和最终产物仍在对应候选事件验证。
- 风险与调整条件：任何新重试/refresh owner、持久会话或浏览器共享认证须明确评审并保持单一状态 owner，不能把模板测试误称产品已认证或浏览器已通过。

## ADR-20261001-002：Web 与 Extension 默认使用 Ky HTTP 传输

- 状态：Accepted；依据用户确认采用兼容 Web 与 Extension 的请求库。
- 背景：原有原生 Fetch client 已集中维护受控 BaseURL、认证并发、401、截止时间与错误处理；采用通用请求库时必须保留这些行为，并支持 Chrome MV3 service worker 和 Firefox MV2 后台页。
- 决定：两种终端项目声明 Ky 运行时依赖，生成的 client 默认通过 Ky 返回原始 Response。关闭 Ky 的自动重试、timeout、totalTimeout 和 HTTP 抛错，由既有请求上下文与调用方/Query 继续处理；受控自定义 Fetch 注入接口保持兼容。当前初始化版本由 manifest 与 lockfile 固定。
- 影响：生成器、依赖最低版本门禁、请求源码/非空测试、源与派生数据规范采用同一合同。OpenAPI、GraphQL、SSE、RxJS 保持按真实消费者引入；Ky 不改变双浏览器的权限、CORS 或生命周期规则。
- 理由：Ky 基于浏览器 Fetch，MIT 许可且无额外运行时依赖，适用于页面和 Worker；避免为 Chrome service worker 引入 XMLHttpRequest adapter，并保留标准 Request/Response/AbortSignal。
- 风险：Ky 与调用方的重试/超时可能叠加，HTTPError 也可能抢先拦截 401；固定默认值和实际经过 Ky 的回归测试防止这些漂移。单元传输测试不能证明真实浏览器 endpoint 与权限兼容。
- 验证合同：真实 Ky 传输回归覆盖 Response/body、header、redirect 配置、401/429/5xx、网络失败、取消与超时；完整生成认证竞态测试和双宿主初始化/负向门禁共同验证。正式候选继续按双浏览器验收规则执行。
- 调整条件：出现已验证的目标浏览器不兼容、可信 OpenAPI 消费者或现有 Axios 生态需求时按 DATA_ACCESS 评估具体 adapter，继续复用单一请求上下文。

## ADR-20261001-001：Extension 单包同时维护 Chrome MV3 与 Firefox MV2

- 状态：Accepted；依据当前用户明确要求增加 Firefox MV2，并要求未来开发自行保证双浏览器差异与兼容。
- 背景：旧合同只有 Chrome MV3，Plasmo 框架支持 Firefox MV2，但共享 manifest_version=3 会覆盖 MV2 工厂，单目标检查也不能发现 Firefox 独有问题。
- 决定：保留唯一 projectType=extension、平铺单包与共用 UI/身份/Logo，固定 Chrome MV3 和 Firefox MV2 两个构建/打包目标。最终 manifest 由 Plasmo 按目标动态生成，共享 override 不固定 manifest_version；两个实际产物逐个检查，任一缺失或失败都拒绝整体候选。
- 影响：实例化、品牌刷新、dev:firefox、构建、打包、升级所有权、验证与 Skills 采用同一合同。未来执行 Agent 自行核对并适配 API、异步消息、权限、后台生命周期、CSP/资源和 URL 差异，日常变化覆盖受影响目标，候选硬要求下逐浏览器验证。
- 理由：两浏览器属于同一扩展产品的目标差异，单包可由 Plasmo 派生基础 manifest；业务兼容仍须明确由开发者保证，不以双目标构建代替运行证据。
- 风险：Firefox MV2 后台页、异步 API 和权限行为与 Chrome MV3 不完全一致；临时加载不代表 AMO 签名/分发。发布时按实际产品确认 Gecko ID 和数据收集声明，不伪造中性元数据。
- 验证合同：构建编排回归、双目录 manifest/身份/locale/入口及 Firefox 独有失败回归，源 validate:harness；真实浏览器、签名与商店验证在对应候选/发布事件执行，未执行必须标记 Unverified。
- 恢复/调整条件：官方目标能力变化或产品明确缩减浏览器支持时，由用户批准新的公开兼容边界并同步生成器、Skills、事实源及回归；不能静默跳过 Firefox。

## ADR-20260930-002：同一发布复用 E2E 选择与已有发布授权

- 状态：Accepted
- 背景：用户明确要求移除“E2E 选择不得跨构建复用”和“发布请求后还要另行授权推送”两项重复门禁；修复、发布元数据更新和打包不应重复索取已作出的决定。
- 决定：同一发布流程内复用已明确的 E2E 选择，每次 CLI 显式传值；仅在尚无选择且无硬要求时询问一次，有硬要求时执行 enabled。明确发布请求覆盖既有目的地及范围内的必要提交、push 和发布步骤，不重复确认；新增目的地、渠道或范围外副作用才补充授权。
- 影响：源规则、Skills、生成下游文档、CLI 缺参提示和正文验证器采用统一语义；不增加策略字段、选择缓存或依赖。此决定取代 ADR-20260919-002 中每次构建单独取得 E2E 的表述，以及 ADR-20260909-005 中已明确发布请求仍需独立推送授权的表述；初始化不配置远端与 smoke 独立解析继续有效。
- 理由：沿用用户已确认的选择和范围，同时避免把必要发布步骤拆成重复确认。
- 风险：发布目标或请求范围发生变化时需要识别边界；仅要求准备候选或验收不触发外部发布。
- 验证：正文合同回归覆盖选择复用、精确新候选验收和发布授权延续；双宿主生成检查覆盖规则传播。复用开关不复用旧产物的验证证据，重新构建或打包后仍验收新字节。
- 调整条件：用户明确改变 E2E 选择、发布目标或授权范围时以后续请求为准；仅永久策略值变更才更新持久偏好。

## ADR-20260930-001：Extension 采用入口内代码路由，双宿主提供亮暗主题

- 修订：其中原生 Fetch 默认传输由 ADR-20261001-002 取代，请求上下文与其他决定保持有效。
- 状态：Accepted
- 背景：用户明确要求 Extension 基线支持 Router，并要求 Web 与 Extension 有基础亮暗 Theme。原 Extension 无 Router、单色 `brand` tuple 和默认 light 与新基线冲突；网络与 GraphQL 仍需保留中性模板的安全请求边界。
- 决定：Extension 将 TanStack Router 声明为运行时依赖，Popup 与 Options 分别实例化代码路由，使用 memory history 和 hash history；不安装 Web 文件路由 CLI/plugin，也不复用 Web 列表路由恢复契约。两种宿主从品牌主色生成十阶色，默认跟随系统，并允许亮色/暗色显式切换，以项目 ID 命名的 localStorage 键保存偏好。原生 Fetch client 与 TanStack Query 继续作为网络基础；GraphQL 在真实 schema 与 endpoint 出现后按 `docs/DATA_ACCESS.md` 选 `graphql-request`、Code Generator client preset，必要时才增设 Apollo。
- 影响：Extension 生成包增加 `@tanstack/react-router`；两种下游新增主题色阶、外观控件与 i18n 资源，原 Extension 两入口各自拥有 Router。此决定取代 ADR-20260922-001 中“无 Router 基线”和 ADR-20260919-003 中“默认 light”的局部结论，其余状态所有权和 Web 列表约束继续有效。
- 理由：路由能力直接满足新基线；按入口选择历史机制与 Plasmo 的独立页面生命周期匹配。语义颜色和系统偏好让两个宿主在亮暗模式下采用同一套组件规则，而不需要额外 Chrome 权限或第二主题系统。
- 风险：Popup 内存导航在关闭后消失，Options hash 路径会出现在地址栏；派生品牌色不能代替真实产品的 WCAG 对比度检查。GraphQL adapter 若绕过既有 client 会遗漏认证、超时、取消和脱敏规则。
- 验证：双宿主生成回归覆盖依赖、路由历史、主题资源与无额外权限；`pnpm validate:harness` 校验源规则。真实下游发布仍须按候选门禁验证构建与 Chrome 行为。
- 调整条件：出现实际 Extension 多页导航、持久恢复或产品设计色板要求时，按真实场景扩展路由树与品牌色阶，并验证 Popup/Options 的生命周期与可访问性。

## ADR-20260922-001：React Web 列表采用 Router 单权威启动恢复与宿主裁剪

- 状态：Accepted
- 修订：其中“Extension 无 Router 基线”由 ADR-20260930-001 取代；Web 列表 Skill 的宿主裁剪与状态所有权仍有效。
- 背景：生成基线已用 `src/pagination/` 统一 1-based page/pageSize 和 sessionStorage 恢复，但可分享、可书签的 React Web 列表又需要 Router search 表达已应用筛选、排序与页码。若直接同步 URL 与 sessionStorage，会形成双 owner；若把桌面列表能力原样派生到 Extension，又会违反单宿主和无 Router 基线。
- 决定：源 Harness 新增 canonical `$web-implement-list-view`，Web 终端保留，Extension 终端裁掉。Web 列表继续复用 `src/pagination/` 的 1-based/pageSize 契约，但 Router search 始终是已应用搜索、筛选、排序、页码与 pageSize 的运行时 owner。原始 URL 包含任一 owned key 时不读旧会话；完全无 owned key 时才按稳定 `listId` 读取一次 sessionStorage 启动快照，并在首次 Query 前 canonical `replace`。业务行、`total`、错误与请求结果只属于 Query/feature。
- 影响：源 Harness 从 16 个 Skills 增至 17 个；Web 终端保留 15 个，Extension 终端保留 14 个。Mantine/Query 基线升至受管列表资产要求的版本；列表仍根据信息结构选择 Table、卡片或搜索形态，不强制选择、列偏好或 DnD。中性初始化不生成业务列表或预装图标/DnD 依赖。
- 理由：该设计保留 URL 的可分享与导航语义，同时在无参数首次进入时提供标签页内恢复，且不引入双向 effect 和状态竞态。按宿主裁剪让 Extension 继续遵守 Popup/Options、消息与 Storage 生命周期。
- 风险：实现者可能从 Router 的默认后 search 错判原始 URL 是否显式含 key，或把 sessionStorage 快照重构为第二状态源；通用空页回首页与已知 `total` 的路由列表回末页也可能被错误合并。
- 验证：Harness validator 校验 Skill 路由、必需 references/资产、可执行契约、Web/Extension 裁剪与升级 ownership；列表纯函数契约覆盖 URL/session 恢复、响应校验、越界纠页、选择裁剪和列偏好迁移，下游仍需补实际页面的 Vitest/Testing Library 测试。
- 调整条件：只有未来路由层提供等价的结构化启动恢复原语，或 Extension 引入可证明同等导航语义且符合其生命周期的真实产品需求时，才重新评估该封闭例外与宿主裁剪。

## ADR-20260919-001：永久 Agent policy 变更采用确定性记录语义

- 状态：Accepted
- 背景：把永久策略是否算“长期决定”留给临场判断，会让同类策略变更有时写 ADR、有时不写；临时 Task 约束也可能被错误持久化。
- 决定：任何初始化后的永久 Agent policy 变更都必须由用户明确确认并写入当日 ADR；目标值相同按幂等 no-op；临时 Task 限制不得改写持久策略。推荐预设关闭内部 `codex/unit-*` 写入并行，但不限制用户明确创建的左侧 Git Task。
- 影响：策略文档、初始化表单、解析器、生成下游与静态合同采用同一五字段语义；既有下游策略不因源推荐值变化而自动迁移。
- 理由：让持久决策可追溯且不依赖 Agent 的主观分级，同时把一次性执行限制与项目策略分开。
- 风险：每次真实永久策略变更会增加少量记录成本；同值 no-op 不写重复记录。
- 验证：策略正负向解析、推荐预设、生成下游正文与必需片段测试。
- 调整条件：只有未来引入同等可审计的结构化策略事件日志时才可替换 ADR 记录。

## ADR-20260919-002：完整候选 smoke 与当次 E2E 独立解析

- 状态：Accepted
- 修订：每次构建单独取得 E2E 的表述由 ADR-20260930-002 取代；smoke 独立解析与精确候选验证继续有效。
- 背景：`acceptance_smoke` 已持久化却未被完整候选验收稳定消费，且容易与每次构建单独取得的 E2E 选择混为一谈。
- 决定：`acceptance_smoke` 只在完整候选验收中解析；用户、产品、安全或渠道硬要求优先，否则 `enabled` 为 `required`、`disabled` 为 `not-required`，源 Harness 的 `pending` 在无硬要求时也是 `not-required` 且不得推断推荐预设。smoke 与 E2E 独立记录、互不替代，只能针对精确最终候选运行。
- 影响：验证 Skill、发布文档、日志规则、生命周期说明、源与下游 validator 使用同一决策矩阵；日常实现和初始化不消费 smoke 或 E2E。
- 理由：持久偏好、一次性构建选择与外部硬要求各自拥有清晰授权边界。
- 风险：维护者需要同时报告两项门禁；显式结果比隐含推断更可靠。
- 验证：源策略必需片段、生成下游 Skill 与策略正文、负向漂移测试。
- 调整条件：只有候选验收协议能以更强的结构化结果统一表达两项独立门禁时才可迁移。

## ADR-20260919-003：中性模板按状态真实所有者和语义交互生成

- 状态：Accepted
- 修订：其中“中性 UI 默认 light”由 ADR-20260930-001 取代；其余状态所有权与语义交互决定仍有效。
- 背景：单组件计数使用 Jotai、Extension 用恒定品牌值伪装远端 Query，会把依赖展示误当成真实架构；语言、标题、动态状态和父子点击边界也缺少完整行为契约。
- 决定：生成模板的局部计数使用 React state；不生成伪 Query 或展示性全局 atom。可分享导航状态归 Router search、会话态归 `sessionStorage`、远端态归 Query、必要跨组件客户端态归 Jotai，且同一状态只有一个所有者。中性 UI 默认 light、由 Mantine theme 管字体与语义令牌，语言切换同步 `<html lang>`，动态计数使用 live region，Extension 使用顶层 `h1`，子控件与外围容器分别测试。
- 影响：Web/Extension 模板、主题、样式、i18n 控制器、生成测试和 UI/数据规范同步改变；相关依赖仍保留给真实需求使用。
- 理由：脚手架应展示最小正确模式，而不是为了证明依赖存在而制造生产反模式。
- 风险：新下游初始代码少了 Query/Jotai 使用示例；文档和真实功能触发时的约束比伪示例更安全。
- 验证：双宿主实例化断言、生成组件行为测试、语言控制器测试与源模板静态合同。
- 调整条件：只有中性模板获得真实跨组件或远端状态需求时，才在对应所有者中增加最小实现。

## ADR-20260909-001：采用事件驱动 Agent 执行与唯一 Task 标题

- 状态：Accepted
- 背景：把普通实现、持久计划、并行、构建和完整验收绑定到任务等级会制造无关步骤；旧四段通用标题还混淆左侧 Task 与内部执行单元。
- 决定：日常范围清楚工作直接实施；Work Plan、并行、构建、E2E、完整验收和发布分别由独立事件触发。用户可见左侧 Task 使用 `Task {序号} | {当前进度} | {单一结果}` 与四态转换；内部 plan、Subagent 和 Worktree 不占用该序号或标题合同。
- 影响：根入口、Agent Policy、Skills、生成下游模板和 validator 使用同一语义。用户可见 Git Task 还必须绑定真实 `threadId`、Git common dir、登记 Worktree 与起始 OID，并以本地提交和 clean 工作树闭环；非 Git Task 绑定精确 cwd。
- 理由：把成本与真实触发器绑定，并让用户拥有的任务与内部执行结构明确分层。
- 风险：宿主标题 API 失败时 UI 可能滞后；失败只报告且不虚写 `已完成`。
- 验证：标题解析、生成入口摘要、Task Skill 合同与负向测试。
- 调整条件：只有宿主提供更强的原子任务身份和状态协议时才替换。

## ADR-20260909-002：初始化冻结 source 事实并一次落盘策略

- 状态：Accepted
- 背景：长时间实例化可能在复制过程中读取到不同 source 状态；逐步写入未决 policy 会暴露中间决策。
- 决定：在 staging 写入前完成项目字段与条件 policy 决议，绑定 source 受管文件的路径、字节、普通权限、`Version.md` 和可用 Git 身份；复制冻结字节并在原子发布前复核。最终 policy 一次写入且不含 `pending`。目标侧以同名 sibling 租约串行化受支持入口，并绑定父目录、staging、holding 与预存空目标身份。
- 影响：交互式初始化首轮批量收集基础字段，再按选择追问；非交互模式显式提供 policy mode 与确认来源。漂移时拒绝发布或清理替代树。
- 理由：保证发布目标对应单一可复核输入快照，失败只留下可回收 sibling staging。
- 风险：大仓库快照增加少量 I/O；Node 标准库没有跨平台目录 `rename-if-absent`，故意绕过租约的同机进程不在协议保证内。
- 验证：source/Version/Git 漂移、符号链接根、无效 policy 零写入、并发租约、父目录替换、目标出现与空目录 inode 回归。
- 调整条件：只有能提供等价内容寻址、模式与 Git 绑定的事务接口才可替换。

## ADR-20260909-003：下游升级使用不可弱化所有权与双基线

- 状态：Accepted
- 背景：单一摘要无法区分 upstream 更新与下游本地偏离；目录复制会覆盖产品代码、身份、品牌、策略和项目记忆。
- 决定：升级器只接受自身生产 ownership manifest，未知路径默认 `protected`，文档默认 `merge-sections`，并为每个受管或混合路径记录上一轮 candidate 与 target 双快照。每轮先生成外部只读三方 plan，只对批准的现有 managed `update` 原子应用单路径，每次写后重规划，最后 record。
- 影响：protected/tombstone、unknown、required source、符号链接、Git/计划漂移全部失败关闭；源日常 validator 复用生产 manifest 解析器校验所有权合同。
- 理由：三方事实能稳定识别更新、本地保留、冲突和人工合并，并限制授权范围。
- 风险：初次 bootstrap 需要人工收敛重叠 managed 路径，这是缺少可信共同祖先时的必要成本。
- 验证：隔离 Git fixture 覆盖 bootstrap、双基线、apply、manual merge、tombstone、计划漂移和稳定退出码；源门禁覆盖 manifest 漂移。
- 调整条件：只有新 schema 保持同等或更强的来源证明与本地保护时才可迁移。

## ADR-20260909-004：模板源拒绝下游产品业务

- 状态：Accepted
- 背景：若 Agent 在 Harness 源分析下游产品需求，会把模板工程与尚未建立身份、宿主和记忆边界的产品语义混在一起。
- 决定：源根只接收 Harness 自身维护和固定初始化字段；任何下游产品目的、场景、业务、专属 UI/文案/数据、远程凭据、产品构建或发布需求在读取、分析、复述或记录前拒绝。产品定义只允许在含有效 `.harness/project.json` 的下游进行。
- 影响：混合请求只能解析允许的初始化字段；实例化成功或切换到既有下游后，用户必须在该唯一项目根重新提出产品内容。
- 理由：确保源模板产品中立，并让每项产品事实从一开始归属于唯一终端仓库。
- 风险：用户需要在新项目中再次提出产品需求，这是隔离边界的必要成本。
- 验证：源/下游识别、混合请求拒绝与 `web-define-product` 准入由 validator 和生成检查覆盖。
- 调整条件：只有未来存在能在写入前证明目标唯一身份与隔离记忆的原子交接协议时才可替换。

## ADR-20260909-005：下游以唯一中性提交建立所有 Task 基线

- 状态：Accepted
- 修订：已明确发布请求仍需独立推送授权的表述由 ADR-20260930-002 取代；初始化无远端与中性基线继续有效。
- 背景：无 HEAD 的新下游无法满足 Git Task 和内部 Worktree 从干净已提交基线创建的门禁。
- 决定：初始化在 staging 检查和裁剪完成后配置受管 repo-local 身份与模板，并创建恰好一个 `chore: initialize project` root commit；不配置远端。此后所有 Git Task 从派发前记录的完整已提交 OID 创建并精确复核。
- 影响：Web/Extension 下游立即具备可复现任务基线；提交之外的远端、推送、标签和发布仍需独立授权。
- 理由：以单一中性提交闭合初始化与任务治理，不引入桌面分支发布链。
- 风险：身份或模板冲突会在原子发布前阻断初始化；失败 staging 按安全清理规则处理。
- 验证：实例化证明单一 root commit、精确主题、clean、无远端；Task 门禁覆盖缺少提交、OID 漂移和脏状态。
- 调整条件：只有任务基础设施支持等价的不可变内容快照身份时才可替换提交 OID。

## ADR-20260909-006：根入口预算化并机械拒绝计划状态矛盾

- 状态：Accepted
- 背景：根 `AGENTS.md` 容易膨胀为详细规则副本；按日 Work Plan 也可能让未完成 Todo 与候选已验收结论并存。
- 决定：根入口固定为合法 UTF-8、最多 20000 bytes 和 120 个物理行的渐进式索引；活动 Work Plan 必须解析稳定 Todo ID 与四态，只要存在非 `done` Todo，就拒绝已验收、已就绪、可发布或等价候选结论。
- 影响：`pnpm validate:harness` 先验证根入口预算、章节与渐进语义，再验证唯一当前 Work Plan 的状态一致性；计划仍只由独立事件触发。
- 理由：保持高频入口可控，并让计划机械状态不能领先真实门禁。
- 风险：入口文案或章节改名需要同步 validator；自然语言负例需防止误伤未来条件或待办描述。
- 验证：真实入口正例、编码/字节/行数超限、语义缺失、配方回流和未完成 Todo 搭配肯定结论的回归。
- 调整条件：只有宿主提供更强的分层指令载入与结构化计划状态协议时才可替换。
