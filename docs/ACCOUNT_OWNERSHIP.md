# Auth 标准：用户、组织与权限

完整账号核心与协作 UI 分开：自有组织、有效成员、本人资料及改密必须保留；用户明确暂不邀请/加入时按核心操作装配。identity.workspace 只在完整协作范围被采用时展开，不能用它恢复已取消的首版操作。后端通用身份/组织能力不代表产品已启用协作页面，也不代表所有成员已有业务权限。

所有采用用户系统的下游复用本基线。账号是全局身份，组织是共享数据的租户边界，组织成员是授权主体。ToC 默认使用自有组织；ToB 加入组织协作，底层归属不变。纯公开或纯本地项目没有账号需求时不创建这些表。

## Auth 需求解释铁律

采用账号与组织基线的产品，必须优先按以下默认语义理解需求，并贯穿需求分析、PRD、原型、接口和实现。不得从含糊表达自行发明额外功能：

1. 用户提及“同一个功能切换查看不同数据”，通常指切换当前组织、查看各组织下的数据。同一功能保持一个入口，读取当前组织作用域；不据此拆出“我的／加入的”功能，或另建平行的数据空间、榜单切换与成员体系。
2. 用户提及“人员／成员”，通常指当前组织下的有效组织成员，复用已有 OrganizationUser 关系和可信成员来源。业务页面可展示这批成员的排名、统计或已明确的筛选结果；独立业务资源实体不构成创建第二套成员资格的依据。
3. 邀请、加入、退出、移除、昵称及角色维护复用已采用的组织成员流程，不另建业务成员档案、邀请关系或重复维护入口。即使只是只读投影，也不能因此额外生成没有独立用户目标的“业务成员”页面。未采用的协作动作不因本规则自动启用。
4. 组织成员资格与业务权限分开。查看或操作业务仍按当前组织的真实权限校验；复用组织成员不授予管理权或跨组织访问权，切换后继续隔离旧权限、请求与数据。
5. 用户明确要求独立业务身份、参与资格、人员模型或跨组织汇总时，尊重该明确需求，在 PRD 中说明其与账号、组织成员的关系及单独维护的必要性。已有明确答案直接复用；只有会改变归属且现有事实无法判断的真实歧义才澄清，不为默认组织解释逐项索要确认。
6. 这条铁律约束需求解释和功能边界，不授权改写外部服务契约、迁移或删除存量成员数据，也不要求无账号的公开或纯本地功能增加 Auth。既有模型或可信契约有差异时明确记录并按当前授权处理。

## 八张核心表与不变量

| 实体 / 表                                         | 固定关系与约束                                                                                                    |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Account / accounts                                | 全局登录身份与个人资料；current_organization_id 仅为账号级组织选择偏好，绝不是授权                                |
| Org / orgs                                        | owner_id 唯一；每个有效账号开户时恰好创建一个自有组织                                                             |
| OrganizationUser / organization_users             | 独立成员 ID；(organization_id, account_id) 唯一，(organization_id, id) 复合唯一；有 active/removed 状态与并发版本 |
| Permission / permissions                          | 服务声明的组织动作目录，code 唯一；没有浏览器增添权限码入口                                                       |
| OrganizationRole / organization_roles             | 组织内 RBAC 角色；(organization_id, code) 与 (organization_id, id) 唯一，带保护状态和版本                         |
| RolePermission / role_permissions                 | (role_id, permission_id) 唯一；角色拥有权限，成员没有直接权限表                                                   |
| OrganizationUserRole / organization_user_roles    | (organization_user_id, role_id) 唯一；两条复合外键保证成员和角色属于同一组织                                      |
| OrganizationInvitation / organization_invitations | 组织与受邀账号唯一槽位；绑定邀请人、有效期、状态和签发版本                                                        |

开户在同一事务内创建 Account、自有 Org、owner OrganizationUser、受保护 owner/member 角色、角色权限和 owner 成员角色绑定，失败全部回滚。owner 必须有真实成员和角色绑定。注册、导入和其他开户路径必须复用同一事务规则，不能直接插入孤立账号。本基线没有删除、转让自有组织或创建第二个自有组织的命令；不通过后台脚本绕过这些约束。

加入只增加另一条成员关系，保留自有组织和原有数据，不复制权限。A 与 B 可以互相加入；成员关系不传递。移除成员只撤销该关系及其权限，不删除、转移组织内容，不禁用全局账号。重新加入恢复同一成员身份行并增加版本，旧权限清空，旧授权/移除请求因版本不符而拒绝。

RBAC 固定为“组织成员 → 成员角色 → 组织角色 → 角色权限 → 权限 code”。有效权限取已绑定且有效角色的权限并集。owner 也必须沿这条链取得权限，没有 owner 名称旁路。owner 角色获得服务显式声明的全部组织权限，基础 member 角色只含 team.leave，不赋予业务数据权限。下表中的细粒度组织管理权限可以通过自定义角色授予；平台级权限独立于本目录，不存在通配符或默认超级管理员。

有效成员凭对应读取码及动作码管理本组织角色、角色权限与成员角色分配；创建、修改和分配角色都不得授出操作者自己没有的权限。系统 owner/member 角色不允许编辑、删除或由客户端分配，拥有者成员不能被移除或修改角色绑定；这些是对象保护，不代替 RBAC。自定义角色的代码在组织内唯一且不可改；删除后历史代码不复用。角色权限修改和删除立即影响全部绑定成员，版本防止并发覆盖；删除角色清理绑定并推进受影响成员版本。重新加入仅恢复基础 member 角色，不继承历史业务角色。每组织最多 100 个有效角色（含系统角色），查询和候选范围均有界。

前端页面、导航、按钮和提交前检查只依据服务返回的有效权限 code，禁止按角色名、role === owner 或 ownerAccountId 推导授权。角色名只用于展示及配置；受保护角色、不可移除的拥有者等对象状态来自服务投影。后端每次请求重新计算 RBAC 并校验组织和对象归属，不信任前端角色列表、权限快照或隐藏状态。

## 业务数据必须显式选择归属

| 数据                   | 持久化归属                                                  | 查询与授权                                                                 |
| ---------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| 全局个人资料与登录凭据 | account_id                                                  | 校验认证账号；切换组织不改变个人资料                                       |
| 组织共享资源           | organization_id，Go 嵌入 TeamOwned                          | 先校验当前有效成员与动作权限，再按目标资源的 organization_id 约束查询      |
| 组织内成员私有资源     | organization_id + organization_user_id，Go 嵌入 MemberOwned | 同时校验组织及成员主体；复合外键禁止组织与成员错配，owner 也不绕过私有归属 |
| 操作追溯               | 组织归属 + created_by_organization_user_id 等操作者字段     | 创建者只是审计字段，不能作为共享资源分区键                                 |

订单、钱包等领域必须在其合同中明确采用账号所有、组织共享还是成员私有，不按模块名称推断。已存在的成员 actor 分区测试仅能证明成员隔离，不能当作组织共享证据，也不能静默重解释已有数据。

后端领域仓储必须在实际读写的同一事务内调用 RequireTeamResource，传入认证 account、请求组织、数据库实体真实 organization_id、私有主体（共享为 0）和服务定义的动作码；随后 SQL 继续带组织过滤。不能把请求中的组织 ID 同时当作对象的真实归属，也不能先在独立事务 Require 再无条件写入。集合和 total 均须经过同样的租户过滤。TeamStore.Write 在读取授权前取得 SQLite 写锁，撤权与业务写入串行；使用其他数据库前必须另行落实等效事务锁和迁移，不将当前 SQLite 验证外推。

## 邀请与当前组织

“加入另一个账号”指加入该账号的组织，不是把两个账号的数据并到一起。没有协作需求的账号仍在自己的组织中使用。同一业务复用相同功能入口，按当前组织读取数据；不因自有／加入关系复制导航或列表，跨组织汇总只在用户明确要求且服务授权时采用。账号菜单以“切换组织”动作打开弹窗，组织信息只在业务正文、组织管理和切换弹窗显示，Header 不显示组织卡片；单组织时保留入口，弹窗中当前项禁用。界面及需求文档统一使用“组织”，现有 Team*、team.*、表名与接口标识保持技术兼容。

有 team.members.read 与 team.members.invite 权限的有效成员按已注册账号邮箱定向邀请，七天有效；同一待接受邀请重复提交返回原邀请。只有绑定账号可接受或拒绝，撤销要求该组织有效成员及 team.members.read、team.members.invite 权限。接受在同一事务改变邀请状态并建立成员；重复同版接受幂等。过期、已撤销、旧版本和他人接受均不能创建成员。续发增加版本，旧请求不能消费新邀请。为保证恢复上下文有界，每个账号最多 100 个有效组织（含自有组织）。

接受后保持原工作组织，由用户显式切换。当前选择保存在账号，多个设备消费同一偏好；每次读取仍重新验证成员。若当前成员已被移除，权威上下文回落自有组织；缺少自有组织或 owner 成员是数据错误，前端不静默补造。自有 profile 与当前 teamContext 各有明确语义，不能混用。

前端唯一上下文包含 accountId、organizationId、organizationUserId 和代次；完整账号装配提供 currentDataOwnership。Query key 包含实际归属、作用域、语言与条件。切换前取消旧私有查询、阻断写入，恢复新成员与权限后再放行。迟到响应和回调不能写入新作用域。权限快照不持久化，也不是后端授权依据。普通业务 403 不注销全局账号。

## 实际装配入口

1. 工程初始化仍只生成中性服务。首次用户实施执行 go-implement-service/scripts/install-users.ts，自建服务同时装配账号与组织 overlay、八表 RBAC、REST 命令和真实 gqlgen 查询。--check 只生成冻结计划；不写目标或运行生成。真实代码生成在隔离副本完成，通过后复核并写回目标；失败保留原服务。
2. 完整协作使用 identity.workspace；identity 模块默认提供该预设，明确收敛协作时按核心操作装配并保留自有组织、成员及个人设置。identity.session 是明确按操作选择的底层会话 helper，不能单独作为完整用户系统交付。
3. 自建 Go 服务使用 workspace-implement-users/scripts/assemble-account.ts 的 goAccountApplicationFiles(base, options)。调用方提供真实 HomePage、宿主与业务页面/动作权限，helper 接通 identity、organization、permissions adapters、协议桥与组织恢复；仅显式 workspace 展开邀请、角色管理和成员角色分配。注册按需求启用；自建邮箱注册自动补齐验证码及开发投递回显，真实投递不回显。
4. 已有服务需提供等效可信合同；不能因为选中 identity.workspace 就推断外部服务已有这些表或接口。已有产品、存量账号与业务数据不自动重装或迁移。

前后端接口字段与操作见 [Go 客户端合同](GO_CLIENT_CONTRACT.md)，生成能力不代表任何具体产品或最终候选已经验收。

## 前后端标准交互与权限表

账号触发器仅显示单一昵称（否则用户名）、头像和展开指示；下拉菜单统一无图标，不重复姓名或邮箱，依次提供切换组织、个人设置、修改密码、分隔线和退出。前三项均打开弹窗，保持底层地址和草稿。个人设置只读取账号邮箱、修改全局昵称；修改密码使用独立表单，不依赖组织查询或业务权限。兼容 `/account/settings`、`/account/password` 地址仍复用同一弹窗。二者都不进入业务侧栏。公开语言／外观 `/settings` 保留独立入口。

没有个人空间。自有组织和加入组织采用同一模型。“切换组织”弹窗显示本人已加入且有效的全部组织，当前项禁用，只能选其他组织并确认；无当前选择时可首次选择。本人收到的站内邀请在弹窗内接受或拒绝，接受保留自有组织和当前选择，随后显式切换。定向邀请只支持已注册且有效的账号，不宣称已发送邮件或生成邀请链接。

侧栏的“组织管理”一级菜单包含组织设置、成员管理、角色管理；各子页只由对应读取权限决定显示和访问，无可见子项时隐藏父分组。完整协作 `identity.workspace` 接通三页；单独 `organization.manage` 仅接组织设置，不暗中启用协作。以下代码是本地 Go overlay 的真实目录；外部服务必须先核对其可信合同。

| 页面／操作         | 权限 code                       | 附加要求                                       |
| ------------------ | ------------------------------- | ---------------------------------------------- |
| 查看组织设置       | `team.settings.read`            | 当前有效成员                                   |
| 修改组织名称       | `team.settings.update`          | 同时具备 settings.read；trim 后 1–60 字        |
| 查看成员列表       | `team.members.read`             | 当前组织分页                                   |
| 邀请／撤销邀请     | `team.members.invite`           | 同时具备 members.read                          |
| 移除成员           | `team.members.remove`           | 同时具备 members.read；保护拥有者和自身        |
| 修改组织内成员昵称 | `team.members.nickname.update`  | 同时具备 members.read；trim 后 1–64 字         |
| 设置成员角色       | `team.members.roles.assign`     | 同时具备 members.read；禁止改自身角色          |
| 查看角色列表       | `team.roles.read`               | 当前组织分页                                   |
| 新增角色           | `team.roles.create`             | 同时具备 roles.read；界面创建空权限角色        |
| 删除角色           | `team.roles.delete`             | 同时具备 roles.read；服务端 canManage 对象校验 |
| 配置角色权限       | `team.roles.permissions.update` | 同时具备 roles.read；服务端 canManage 对象校验 |

拥有者沿受保护 owner 角色获得服务声明的全部组织权限；成员的权限来自多角色并集，基础 member 仅有 `team.leave`。业务权限由其领域显式注册，Auth 不附带产品权限。前端不凭 owner 名称、账号拥有关系或角色显示名放行。系统角色不可编辑、删除或手动分配；基础绑定由服务保留，客户端原样回传基础 ID 不授予额外能力。

非拥有者不能编辑或删除自己当前绑定的角色，也不能操作原权限超出自身上限的角色。分配成员角色时，对新增及撤销的绑定都检查权限上限；候选只返回可授予自定义角色，前端必须保留已有但不可见的绑定。角色代码在组织内唯一、删除后不复用，格式为 `^[a-z][a-z0-9._-]{0,63}$`，名称 1–60 字；每组织最多 100 个有效角色。

组织昵称持久化在 OrganizationUser，使用成员版本控制，展示回退到全局昵称／用户名；不修改全局账号或其他组织。角色投影含 `canManage`，成员投影含与 `roleIds` 对齐的 `roleNames`。`teamAssignableRoles` 只需 members.read + members.roles.assign，不要求 roles.read，也不通过完整角色目录扩大读取。

切换由唯一 coordinator 执行：阻断旧私有 UI → 取消并移除私有缓存 → 提交切换 → 权威重读当前组织与成员 → 重新获取有效权限 → 恢复正文并重跑路由。响应丢失只权威查询，不能盲目重放切换；账号或代次变化后丢弃迟到结果。

管理写入复用当前账号／组织／成员／代次，同步防重复锁和可取消请求。409 保留草稿，重读目标后由用户决定再次提交；超时、未知结果及成功写入后的读取失败只能只读核对。影响访问的写入成功后先刷新权限，再刷新相关查询和路由。相同主体的权限加载期间保留表单实例、隐藏并禁用交互，确认撤权才卸载；核对和提交共用写锁，旧核对不得解除新命令的未知状态。403 读取重取权限并重跑守卫，不注销有效全局账号。

管理集合通过 GraphQL 返回有界 items/total、稳定 ID 顺序；命令通过 REST，版本和租户约束在同一事务检查。Query key 包含实际账号、组织、成员、代次、语言及分页；Router 唯一拥有 page/pageSize，Web 的 session 快照只在原始 URL 没有这两项时恢复，Extension 使用各自 memory/hash Router 及上下文内快照。读取失败不伪装空列表，不纠正到未经确认的页数。

本地 overlay 初始化事务将旧 `team.manage` 的绑定迁移为原有 10 项管理权限，再停用旧码；新增组织昵称权限只自动授予 owner。迁移幂等，重启不会扩大旧自定义角色授权。原始 Go 来源快照保持字节不变，生成服务通过本地 overlay 和真实 gqlgen 接入新合同；已部署外部服务和现有产品不自动改写。
